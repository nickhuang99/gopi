# Computer Use：第二块蓝海 + 4 原语同构（2026-09-10）

**来源**：nick 与 doubao 的长对话（`~/work/claude/nick/computer_use_doubao_chat.txt`，261 行 / 38.9KB）
**性质**：方向与商业判断层（最高价值层），非实现细节
**记录者**：PA（含对 doubao 分析的三点纠正，见 §四）

---

## 一、核心链条（nick 的第一性原理推演）

```
1. 传统软件是"为人设计的 I/O 闭环"（屏幕 = 眼，键鼠 = 手，输入输出全部闭合）
2. 重写全部软件为 Agent-native = 遥不可及
   理由：存量资产锁死（几十亿行经数十年验证的代码/GUI/工具链）；
         重写编译器这类基础件没有意义——AI 写出来仍需更长时间打磨，代价更大；
         "验证、回归、迁移的代价远比重用更高"
3. 所以必然是混合式 —— 新软件可能适配 Agent 接口，大部分传统软件在原基础上小修小补
4. Computer Use = 复用人类 I/O 通道，非侵入（不读 UI 树、不挂钩子、不需 API）
5. 但经济约束极残酷：替代对象是"低时薪文员"（报销、录入、表单填报）
6. ⇒ 成本权重 > 绝对精度（关键判据）
7. ⇒ 稠密模型（Anthropic）在此经济约束下天然出局（不是精度问题，是单价问题）
8. ⇒ 轻量原生多模态（DeepSeek V4.1 Flash / GLM-5.3 Flash）刚好卡位
9. ⇒ 多模态的真正主战场不是 AIGC（视频/图像生成只是展示面、最小的一部分）
10. ⇒ 而是 Computer Use —— 编程之后的第二块蓝海
```

**第 10 点是 nick 首创**：编程 Agent 改造"创造软件"的环节；Computer Use 改造"使用软件"的环节。后者是存量资产上叠加智能层，迁移成本最低。

---

## 二、经济账（为什么这是市场分层问题，不是技术碾压问题）

| | 文本编程 Agent | Computer Use GUI Agent |
|---|---|---|
| 目标岗位 | 程序员、高级技术白领 | 文员、行政、基础财务、数据录入 |
| 人力单价 | 高 | **低** |
| 单次任务收益 | 大 | 小 |
| token 成本容忍度 | 高（省下工程师几十分钟，ROI 为正） | **极严苛** |
| 现状 | 已爆发，资本/媒体焦点 | 蓝海，尚未进入 |

**残酷点**：如果每轮截图+规划成本达到几分钱，循环十几步完成一个报销表单，成本直接逼近甚至超过人工价值 → 商业闭环断裂。

**反直觉洞察**（doubao 提出，我认同）：**"任务简单 ≠ 技术容易"**。填表单逻辑简单，但经济约束残酷。
- 高成本模型哪怕 95% 准确率，商业上依然不可行
- 低成本模型 85% 准确率 + 自动重试 + 校验层，整体 ROI 反而为正

> **高时薪场景买精度；低时薪批量自动化场景买性价比。**

### 为什么各家不主动大声宣讲
1. 技术尚未成熟（长循环稳定性/GUI 歧义/误操作风险）
2. 社会层面顾虑——直接宣传"可大批量替代基础办公室岗位"会引发舆论/劳工/监管反弹，企业倾向低调试点

## 三、4 原语同构（nick 现场提炼，本对话最有工程价值的一步）

把人类操作员的全部行为压缩到最小集合，与编程 Agent 的原语做同构对照：

| 代码 Agent（文件系统 = 数字状态） | 仪表/屏幕 Agent（面板 = 像素状态） |
|---|---|
| `Read` — 读取状态（观察） | `Capture` — 获取世界状态（观察） |
| `Write`/`Edit`/`Bash` — 修改状态（动作） | `Actuate` — 改变世界（动作） |
| （`sleep`，常被忽略） | `Wait` — 物理世界延迟 |
| （校验返回码） | `Verify` — 二次观察确认动作生效 |

**底层骨架 = ReAct**（Reasoning + Acting，Princeton + Google 2022 论文）：思考 → 调用工具 → 获取观察 → 再思考。
**doubao 的诚实标注**：ReAct 是现成的、已发表的通用基础；**4 原语精简清单 + 与代码 Agent 的同构对比，是顺着对话现场整合提炼的**，非直接抄现成文本。

### 为什么这个同构重要
nick 的原话："**我只实现了它的手和眼睛（Read/Write/Edit/Bash 四个就解决一切问题）。所以只要把这个基本的功能闭环了，它就能实现几乎无限的能力。**"

**这正是 ReAct 范式的杠杆效应** —— 也解释了我们 gopi 只有 16 个工具却能覆盖大量工作（记忆铁律：工具集规模 = 速度，gopi 10 个工具 vs claude 80 个，同任务 5 vs 17.4 分钟）。

## 四、对 doubao 分析的三点纠正（避免优化错方向）

### 纠正 1：混淆了服务端 KV 压缩与客户端上下文管理

doubao 说"HCA+全局 KV 压缩刚好适配 Computer Use 长循环成本"。

但这是**两层正交的东西**：
- **服务端 KV Cache 压缩**（HCA/CSA2）降低的是 **DeepSeek 自身的显存成本** → 部分通过定价传给用户（命中价 0.02 元/百万）
- **客户端上下文管理**（我们的 trim / write_task_area / compaction）降低的是**我们发送的 token 数**

**真正对我们有价值的是第二层，且完全由客户端实现——与 DeepSeek 用不用 HCA 无关。**

### 纠正 2：漏了最关键的项 —— 图像 token 其实不贵

doubao 反复强调"每轮截图产生大量图像 token"、"成本爆炸"。

**实测数据反驳**：deepseek-v4-flash-vision-exp 每图 **≤384 tokens，实际约 56 tokens**（不看原始分辨率）。

**真正的成本大头是历史累积**：
- n(n-1)/2 的缓存命中二次增长（我们实测命中/新增 = **22.4× / 22.9×**）
- 这是 agent 循环每轮重发全部历史前缀的固有结构

> **"看图贵"的叙事放大了视觉成本、低估了上下文管理成本** —— 会导致去优化图像编码，而真正该优化的是上下文压缩策略（我们已在做的 memory-aware）。

### 纠正 3：机器人作为"直接需求端"的时间顺序可疑

doubao 说"计算机屏幕 GUI 属于人造结构化视觉、难度低，所以 Computer Use 是机器人落地的前置简化赛道"。
逻辑成立，但**市场形态被忽略了**：

| 路线 | 市场形态 | 评价 |
|---|---|---|
| 机器人工控看屏（工厂几台老上位机） | 项目制、非标、需现场集成、离散点位 | **非产品化市场** |
| 浏览器/桌面纯软件 GUI Agent | 无硬件、无现场部署、软件分发 | **真正可规模化** |

nick 自己举的坦克/煤矿例子也自评"并不是很恰当"——那些是**极端长尾**，不是起点。
**机器人路线是叙事锚点（有画面感），产品化主战场是纯软件形态。**

## 五、场景二分（可行性判断）

| 场景 | 特征 | 技术条件 |
|---|---|---|
| **文字密集 GUI**（企业老旧业务系统、网页表单、报销界面） | 截图里绝大多数信息是文字，只有按钮/下拉框/输入框等标准控件；视觉负担低（"图像里都是文字，没有其他真实图像"） | **已接近可用原型** — V4 Flash / GLM Flash 这类可直接搭 Vision Harness |
| **通用任意屏幕**（复杂图表、微小控件、动态渲染/动画） | 需要分辨细微像素差异、理解动态动画与图表逻辑 | **还差数年** — 轻量 MoE 多模态在此识别失败率明显上升 |

**短板（原型能跑，不能直接大规模上线）**：
- GUI 歧义（相似按钮、灰色禁用控件、悬浮提示、重叠弹窗）
- 长循环漂移（压缩后的远期记忆丢失，忘记前置约束）
- 容错成本（误点击可能提交错误表单，企业容忍度极低，须叠加校验层）
- 峰值推理延迟（并发截图推理的算力压力）

### 分层架构（行业隐性共识 = 分层降本）
```
底层：轻量 CV/OCR（检测屏幕变化区域、提取文字与边界框）
      → 无大模型 token 开销；屏幕大部分区域不变时只截取变化的局部 patch
中层：状态 KV 压缩（久远历史做重度压缩只留语义摘要；当前画面与最近几步保留精细 KV）
顶层：多模态 Agent（仅在需要决策/理解新弹窗/判断成败时调用昂贵推理）
```
> "螺蛳壳里做道场" —— 把昂贵多模态推理只留给真正需要决策的时刻。

**关键区分**（doubao 提出，好）：多模态模型分两条路线——
- **AIGC 生成侧**（Seedance/可灵/SD 系列）：图像编码器为重建/生成像素服务，冗余多、推理重，GUI 理解只是副产品，**不适合 Computer Use**（这解释了半年前可行性研究结论）
- **Agent 感知侧**（V4 Flash / GLM Flash）：编码器设计目标是"把图像转成语义供规划推理"，优先提取文本/布局/控件结构，**天生适配 GUI**

## 六、对 gopi 的三条可行动推论

### 推论 1：gopi 已具备 Computer Use 的"眼睛和手"
实测链路已完整：
```
截图（Xvfb/xdotool import）→ vision（deepseek-flash 原生多模态，逐字 OCR 精确）
  → gopi agent 规划 → xdotool 注入键鼠动作
```
已验证案例：wine + Xvfb 下 LLM 操作 h3maped 编辑器；M0/M1 实验 LLM 自主玩 HOMM3（进游戏 → 场景选择 → 选英雄 → 回合循环）。

### 推论 2：真正的瓶颈是历史管理，而我们有解
Computer Use 长循环 = **另一个 context 膨胀场景**，与 gopi 长编码会话同构。
我们已有的 memory-aware 机制（write_task_area 提交 / trim / 结论 carry-forward / request-length 封顶 106K）**可直接复用**。

### 推论 3：4 原语是工具面设计的检验标尺
若 Computer Use 真的只需 Capture/Actuate/Wait/Verify，那接 GUI 操作**只需新增极少工具**：
- `capture`（截图/读屏）
- `actuate`（键鼠事件注入）
- Wait → 现有 bash sleep
- Verify → capture 二次调用

**这与"工具集规模 = 速度"的实证一致**（不是加更多工具，而是加对的少数工具）。

## 七、一句话收束

> 编程 Agent 解放**创造软件**的人；Computer Use 解放**使用软件**的人。
> 后者的最大枷锁不是视觉识别精度，是**严苛到极致的单位动作成本** —— 这直接决定稠密模型在这片蓝海只能做小众试点，无法规模化普及。

**而 gopi 的现有能力面（vision + xdotool + agent loop + context compaction）已经覆盖 Computer Use 的核心链路。
M0/M1 的 HOMM3 实验实质上就是 Computer Use 的一个实例 —— 我们已经在做了，只是没这么叫它。**

## 八、落地节奏预判（doubao）

1. **0~1 年**：封闭企业内网、固定业务流程、文字为主的老旧表单/工控 GUI，小批量试点（非侵入 RPA 升级版 = Flash 类多模态 + 前置轻量 CV + KV 压缩）。企业内部私有化部署，不面向大众宣传。
2. **1~3 年**：扩展到网页通用后台，处理更多弹窗/图表，降低错误率。仍限业务域。
3. **3 年以上**：才慢慢靠近通用屏幕操作。

**技术瓶颈排序**（doubao 认为比成本更棘手）：长循环任务漂移 > 误点击造成业务数据损坏 > GUI 微小元素识别歧义 > KV 压缩导致远期记忆衰减。
