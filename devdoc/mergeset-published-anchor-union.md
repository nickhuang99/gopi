# The published-anchor edge has a UNION half — COMMANDS.md drift is caught at the landing

Task `01a12f5d-4c31-7348-91bb-9f2be4b807bf`.

## The defect, measured, not assumed

`COMMANDS.md` publishes `path/file.go:NNN` anchors (54 of them) and a standards
gate reds when one is wrong (`internal/standards`, `TestCommandsDoc*`). The
delivery gate (`internal/tools/task_finish_gendoc.go`) asks the published-anchor
edge about **the branch's own change**, deliberately measured from the merge
base — `git diff --name-only <ref>...<branch>` — so another branch's commit is
never attributed to this one.

**A landing is not one diff.** Two concurrently delivered branches can each be
internally consistent, while the tree they compose has never been generated by
anyone. The measured chain on this repo (2026-10-12):

```
03f2d1dfe 07:40  cmd/agent/cli_doccheck.go routing predicate 118 → 152
93e402d36 13:28  …                                           152 → 161
721268925 16:18  …                                           161 → 194
```

Each of the three moved a published anchor source and **did not touch
COMMANDS.md**; each one's own diff was therefore clean by the delivery gate's
question. The master they landed into carried `cli_doccheck.go:161` in the
document and `:194` in the source — the anchor moved in a commit that never had
the document within its own merge-base diff.

The edge machinery that answers "what does this change oblige?" landed at
`4c2174873` (09:04) — **after** the first of the three commits above.

## The fix: one more member in a membership test

The merged-result measurement already exists and already runs on **every**
landing (`RebuildAfterMergeMergeset`, reached from `RebuildAfterMerge`'s close
loop, `gopi task merge`'s tail, and the merger pass), and **its revision already
IS the union** (`<mergeRev>^ <mergeRev>`, read by the step's own code). So the
union half is the same question asked of the union — no new tool, no new script,
no new resident dependency (Rules 3/35), and nothing new has to be remembered.

`internal/tools/mergeset_gendoc.go` adds, to the run set:

- ② the paths the **landing** brought in (`<mergeRev>^ <mergeRev>`);
- ③④ the paths each **parent** brought in (`<p>^ <p>`) — the two parent legs are
  what make a path that moved no anchor *inside its own branch* visible;
- ⑤ the **document itself**, dropped as an entry and kept as a **FLAG**: the
  edge maps a change onto the *anchor sources* a document publishes, and a
  landing that only touched the document obliges nothing by that rule — yet if
  it *also* brought in a commit that moved one of those sources, the tree it
  left behind carries a document nobody regenerated. So the gates of every
  participating edge run when the landing touched the document.

The membership test asks `internal/gendoc.GeneratedDocAnswer` — **the one
existing edge definition** (Rule 14: one reader, never a second opinion) — and
folds the gate packages it names into the merged-result step's run set.

### Why the parent legs are read two-dot, never three-dot

Three-dot measures **from the merge base**, which is exactly what a landing's
union must not do — the whole defect is the change *outside* the merge base.
The step's own landed-diff read is two-dot; the parent legs match it.

### Honest limits, stated so a later reader does not mistake them for coverage

- A commit that moved a published anchor source **without** touching the
  document is visible here only when it arrives **in** the landing or in one of
  the landing's **two parents**. A commit further back on master is a
  pre-existing state — the **base arm** owns it, the same limit the sibling
  package-scope map has always had, and the same reason a red the base already
  carried is not blamed on the landing.
- A parent leg that cannot be read is **logged and skipped**, not swallowed
  (Rule 15b): the union stays measurable from the landing's own diff, and the
  difference between "the union covers this" and "this leg was not read" is
  never left to be inferred.
- The union is **bounded** (`gendocUnionPathLimit`, 20000 paths); exceeding it
  **abstains with the count**, never a silent widening.
- A tree with no document of record **abstains** with the walk's own counts
  (`candidate(s)`, `edge(s)`), so "the scan found nothing" is distinguishable
  from "the scan never ran".
- A **broken edge** (a document whose generator is not in the tree, or an edge
  with no gate package) is reported as BROKEN — an instruction a reader would
  follow into a command that runs nothing.

### Never a repair, never a rollback

It does not run the generator (rewriting the document is the author's act, not
a gate's), never hand-edits the generated block, and its red is REPORTED through
the merged-result step's own channels with `res.OK` left alone — the sibling
step's contract, unchanged.

## The briefing's second diagnosis was WRONG, and A/B measurement said so

The briefing (and its red proof) claimed that regenerating `COMMANDS.md` would
**not** turn the standards gate green. Measured A/B on this branch: after
`go run internal/standards/testdata/commands-census.go . COMMANDS.md`, all three
`CommandsDoc` tests pass and `--check` exits 0 — i.e. the red proof pointed
**opposite** to the fix direction. The stale row was
`cmd/agent/cli_doccheck.go:161` → `:194`, exactly the third commit of the chain
above. The wrong memory record was corrected with `memory(action=update)`.

## Not done (honest)

- The generator is **not** run by the gate. A landing whose union obliges the
  document's gate will now be **reported red**, not auto-repaired — by design
  (a gate that rewrites a generated file is a second writer of it).
- A commit further back on master that moved an anchor source without the
  document stays invisible to this step; it is the base arm's to report.
