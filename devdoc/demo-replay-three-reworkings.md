# `docs/archive/demo/replay/` 的三次返工 —— 从"文字长图"到"真终端重放"

**这份文档的来源**：`docs/archive/demo/replay/README.md`（2026-10-02 版，24.7K）。那份 README 里
真正不可再生的东西**不是那批图**，而是**三次"上一版为什么错"的推理** —— 每次返工都不是
"图不够好看"，而是**一条判据或一条路径被证明是错的**。图可以重跑，推理不能。

**这份文档记的是推理，不是产物。** 产物（PNG / GIF / frames / 逐张的像素读数）属于
**一次运行的 outcome**：它们由 `docs/archive/demo/replay/` 下的脚本重跑生成，各批已被移除，
判据与工具本身留下（见末节"留了什么、删了什么"）。

---

## 返工一：排版文字 ≠ 界面（`text2img` 路径的根本错误）

**做法（v1）**：把 dump 的**纯文字行**交给 `gopi text2img` 排版 → 14 张 4690px 宽的文字长图。

**为什么错**：**`text2img` 出口必然是"文档"，不是"界面"。** 它丢掉的正是 dump 里
**真实记录着**的三样东西：

| dump 里真实存在的 | v1（排版） | v2（真终端） |
|---|---|---|
| 整屏 **grid 几何**（117×26，含空行与相对位置） | 只取连续几行，重新排版 | 按 117×26 排出**整屏**，空行照 dump 保留 |
| **attr_runs 颜色**（`fg=colour-230` 分隔线、`colour-220 bold` 用户行…） | 全部单色 | 逐行按 dump 自己的色号着色 |
| **输入区 / 状态栏 / 光标**（grid 第 24/25 行） | 完全没有 | `you>` + 光标块 + 状态栏 |

**⇒ 教训**：**"够清晰"和"像界面"是两件事。**
v1 当时**通过了它自己的自查** —— 因为它的判据只有"每字符 ≥16px"这一条。
**一条判据能证明"看得清"，不能证明"是那个东西"。**

**这条教训适用于任何"渲染保真"任务**：判据必须量**那个东西的特征**
（有没有框线、有没有输入区、有没有状态栏），而不是量**它的一个可读性代理**。

**推论（同一次返工的第二次教训）**：v1 的所有资产（14 张长图 + 生成脚本 + 它自己的证据）
**归档而非删除**，理由有两条：① 它们记录了**这次返工为什么发生** —— 读者可以拿旧图和新图
并排看，直接看到"文档 vs 界面"的差别；② 那份 `vision-reads.tsv` 是**旧管线的证据**，它当时
**也通过了自查**，这正是上一条教训的活标本。

**另一条方法上的承诺（不在三次返工里，但同源）**：v2 **没有真开一个 chat 会话去"拍一段新的
对话"**。画面里的对话文字**全部**取自那段真实 dump 的逐字行 —— 换的是**渲染**（真终端 +
真颜色 + 真几何 + 真抓屏），不是**内容**。理由：素材是**真实发生过的工作过程**，重演一遍就
不是同一件事了；而"像不像界面"取决于渲染方式，不取决于重录。

## 返工二：判据的定位模型错了，而且它**假绿**过（2026-10-01 修）

**症状**：同一份 `verify-frames.py` 对 `img/clean` 输出 **0/7**、对 `img-new-vte/clean`
输出 **0/5** —— 而 committed 的 `evidence/four-questions.tsv` 里那一列**全是 NO**。
**那张表本身与它同一次交付里声称的"14/14 通过"矛盾了很久。** 只有 `img-old-xterm` 的
7 张是 ✓✓✓✓。

**根因（像素级，不是"图坏了"）**：光标块的选法是
**"在宽度窗口 [0.6, 1.6] 字格内取横向游程最长的那一行"**。
而正文字形的横向游程可达 **30px = 1.58 字格** —— 落在窗口内，**且比真光标
（19px = 1.00 字格）更长** ⇒ **"取最长"永远选中文字。**

| 帧 | 真光标块 | 旧脚本选中的"块" | 后果 |
|---|---|---|---|
| `img/clean`（vte, 行距 55.08px） | 19×55px，槽 {23,24} | 30px@槽 25 / 11 / 19 / 3 / 7 | 输入区 ✗、框线"输入上方" ✗ |
| `img-old-xterm`（行距 27.15px） | 19×18px，槽 {24} | 19px@槽 24（**恰好**没错） | 旧判据 7/7 —— **假绿** |

**⇒ 老 xterm 臂的 7/7 是"行距小"带来的偶然**：它的字形横向游程恰好等于字格宽，
"取最长"没得可选。**换成任一现代 VTE 终端（21px 行距族）即恒 ✗。**

**修的是什么（判据没放宽）**：光标块改成按**实心矩形**找 —— 宽度仍用同一个
0.6–1.6 字格窗口，另加"竖直方向同一 x 区间、同一颜色上连续 0.5–1.2 个**行槽**"。
**高度是"行"的性质，用 `slot_h` 量；用 `cell` 量高度是单位错误**，会让 55px 的真光标
被判成"太高"。`--min-colours 4` 与 `--min-px-per-char 16` **一个字没动**。

**⇒ 教训**：
1. **"取最长/取最大"这类启发式，在一个域里恰好对，不代表判据对。**
   判据在**一个几何**上通过，必须换另一个几何复验（这里就是三代终端臂：vte 55px 行距 /
   vte 21px 行距族 / xterm 27px 行距）。
2. **单位错误会伪装成判据失败** —— 用"字符格"量高度、用"行槽"量宽度，都是同一类错。
   症状是"判据说图坏了"，而真相是"判据的单位错了"。
3. **一张汇总表的 ✓ 与它同一次交付的散文结论长期矛盾，是一种交付缺陷**，不是"图的问题"：
   committed 的 `four-questions.tsv` 全 NO，而同批 README 写 14/14 —— 两者能并存很久，
   因为**没有任何一处把交付的表连回产生它的判据**。修复时两者必须同源。

## 返工三：判据③ 写成了"图里有墨迹"，不是"最后一行槽有墨迹"

**由负控抓出**：判据 ③ 的实现把契约里的"**最后一个行槽**里有墨迹"写成了
"图里有墨迹"（`last_row_has_ink`）。

**后果**：**擦掉末槽的坏图在四问那一列照样 `✓✓✓✓`**，只靠 `pass` 里的
`status_on_last_row` 兜底。**报告表格里那一列是给人看的，它说 ✓ 就得是 ✓。**

**修法**：`q3 = status_on_last_row and blank_row_before_status` ——
**判据、README 表格、负控 N4 三者同源的唯一判定点在 `judge()`**。

**⇒ 教训**：**一个判据如果只在一个"汇总列"里正确、在"明细列"里错误，
那它对读者就是错的。** 汇总列的 ✓ 必须是明细列的同源结果，不是独立算出来的。

**方法上的推论（为什么负控值得单独立一条测试）**：同一次修复里，负控抓出的缺陷**不止这一个**
——它们都是判据侧的，**帧侧一直是对的**。所以"图一直是好的、判据说它坏"这种局面，
排查顺序应当是**先怀疑判据**（尤其当同一批帧在别的几何上通过时）。

## 判据的最终形态（三条，都量像素）

| 问 | 机械判据 |
|---|---|
| **框线** | 存在这样一行：墨迹跨度 ≥ 98% 图宽 **且** 这跨之内墨迹覆盖率 ≥ 85%（只有连成一条的分隔线满足）；**顶框线**（槽 0）与**输入区上方那条**（倒数第 3 槽）都要在 |
| **输入区** | 倒数第二个行槽里有一个**实心块**：宽 0.6–1.6 个**字格**（cell = 分隔线跨度 ÷ 列数），且**竖直方向同一 x 区间、同一颜色上连续 0.5–1.2 个行槽**（`slot_h` = 图高 ÷ 行数） |
| **状态栏** | **最后一个行槽**里有墨迹（**不是"图里有墨迹"** —— 见返工三），且它与上一行之间隔着一个**空行槽** |
| **颜色** | 非背景墨迹量化后 ≥ 4 个色团（≥200 像素才算一个） |

**行槽归属规则**（这一节的核心契约）：行槽 = 图高按 dump 的行数等分
（`slot_h = H/rows`）。**底部三槽是固定的**：

```
行槽 rows-3 = 分隔线（输入区上方那条，整宽连通）
行槽 rows-2 = 输入行（you> 提示符 + 光标块）
行槽 rows-1 = 状态栏（本帧末行有墨迹，且其上是空行槽）
```

判"某个东西在第 N 槽"时，按**它覆盖的行槽集合**判（`cursor_slots` / `rule_slots`），
**不是只看顶边那一个像素行** —— 实测光标块 `y=1321..1375`：顶边属槽 23、主体属槽 24，
两者都在 `{23, 24}` 里。

机械实现在 `docs/archive/demo/replay/verify-frames.py`（`judge()` 是唯一判定点），它的最小复现测试
是 `docs/archive/demo/replay/test-verify-frames.py`（参照帧全绿 + 5 张负控全拒），**两者都留在树上**。

## 其余留存的教训

### 抓屏要"两次一致"才算画完

不是"睡够 2.2 秒"，而是**连续两次 `gopi capture` 的 `sha256_16` 相同**才算画面画完。
**实测反例**：某一帧只有 143 个墨迹像素行（同批其它帧 300+），
**那是 xterm 还没画完就被拍了 —— 会少几行，而肉眼看不出来。**

**⇒ 与 `gopi replay` 的 settled-frame 修复同源**（见 `devdoc/replay-dropped-frames-verdict.md`：
握手只保证"屏幕不会变"，不保证"终端已经画完这一拍"）。

### vision 与像素测量不一致时，不要取舍，两个都摆出来

**实测**：7 张图 vision 全读成"终端界面/聊天界面"（没有一张被读成"文档/markdown 排版"）。
**但其中四张，vision 对"框线"给的是"无 / 只有中部一条横线"** ——
而**像素测量说这四张的顶框线与输入区上方那条都在**。

**两种解释都摆着，由读者判**：那两条线是 1px 高、与背景对比度低，vision 可能没认出来；
也可能是它把"框线"理解为**围成一圈的盒子**（只有那张拍 banner 的图有）。

**不修改它的原话，也不拿它当唯一裁决** —— **这正是把像素测量放在第一节的原因。**
（另一条同类纪律：`vision_analyze` 读的是**内容**，不是**渲染质量**；量渲染质量用像素比对。）

### raw / clean 两套并存，且"差 0 像素"要如实写

**净化发生在文本进 pty 之前**（不是拍完再涂盒子）：clean 版把身份线索换掉后才打印，
所以它拍到的**就是**净化后的界面。（上一版是拍完再在 PNG 上涂盒子，那会留下两种不同字体的
补丁，且盒子会盖住界面 —— 这也是"渲染保真"在**净化**这一面的同一条教训。）

**实测差异**：四张有差（0.22%–2.02%，差异位置都在含路径/身份线索的行），
**三张差 0 像素** —— 那三段的正文里本来就没有身份线索。

**"差 0 像素不是缺陷，是事实"**：**把它写出来，比让读者以为"净化一定改了图"要诚实。**
配套一条**残渣检查**：干净版跑完后扫绝对路径、会话 id、uuid、内网地址、`user@主机`、
机器名、项目/竞品路径 —— 任何一条命中就 exit 1。

### 隔离：判设备号，不是判路径拼写

* 自建 `Xvfb :78`（2400×900×24，`-nolisten tcp`），收尾随脚本消失；证据里记的是**运行期
  读数**（宿主现有 X server 进程里没有 `:78`、socket 目录里没有 `X78`），不是"我们没起过"。
* 操作者的 `$DISPLAY` 在脚本里出现 **1 次**，就在一行 `echo` 对照输出里，
  **0 次**被当参数传给任何子进程；每处 `gopi capture` 都显式带 `--display` 自己那个号。
* **不注入任何输入**：不调 `gopi act`、不 `xdotool type/key`（拍摄只需画出画面再抓）。
* **证据不落 `/`**：设备号 `2052` vs `/` 的 `2051` —— **判的是设备号，不是路径拼写**
  （`/tmp` 虽然拼写不同，但它和 `/` 是**同一个设备** `2051`，所以证据不放那里）。
  **脚本里这条是硬断言：不等就 FATAL 退出。**
* **源 dump 只读**：全程只有读路径。它属于另一个**仍在运行**的会话，其所有者每隔几秒重写它，
  所以每跑一次都**再记一笔指纹**（sha256 + size + mtime + 行数）。行号在**更早**的位置上不会
  变（那是追加写的历史），这也是行号可以稳定引用的原因。

## 留了什么、删了什么（判据 vs 产物）

判据是**可复用的规矩**，产物是**一次运行的 outcome**。按这条线切：

**留下（判据、来源、净化规则、可重跑的工具）**：`verify-frames.py` + `test-verify-frames.py`
（四问判据与它的最小复现）、`shoot-frames.py` / `shoot-replay.sh`（重跑生成这批图的管线）、
`pxdiff.py` / `arm-metrics.py`（像素差与两臂汇总）、`crop-client.py`（正文锚点）、
`SOURCE-MAP.tsv` / `captions.tsv` / `redaction.json`（同一份数据的来源表、人话、净化规则，
同名副本也在 `terminal/{new-vte,old-xterm}/`）、`evidence/` 与 `evidence-*/`（**逐行/逐张的
读数**，含逐字性核对与残渣检查）、`terminal/` 的 arm 元数据（`replay.json` / `diff-table.tsv`
/ `mask-boxes.json` / `redaction-span.json`）。

**删掉（像素产物）**：`img/` `img-new-vte/` `img-old-xterm/` 三代臂的 42 张 PNG、
`replay-film/` 的成片 15.4MB GIF 与 12 张抽样帧、
`appendix/img-old-text2img/` 的 14 张 v1 文字长图 —— 共 65 个文件 / 25.9MB，
全部由上面留下的脚本重跑生成（`bash docs/archive/demo/replay/shoot-replay.sh`；
v1 那一版由 `appendix/pipeline-text2img/gen-replay.sh` 生成，脚本与它的证据表留下）。

**为什么这次删而上次归档**：归档（上一次）是为了**让读者并排看到"文档 vs 界面"的差别**；
那条推论已经被写进上面的返工一，**图的证据作用已经完成**，而"图可以重跑"是它们的定义性质。
