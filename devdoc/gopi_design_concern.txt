1. EXECUTIVE SUMMARY
====================

GoPi is a Go-based ReAct-loop coding agent (~500 lines of core logic) that
replicates the essential architecture of pi-mono's agent-loop.ts (792 lines).
It is a remarkable prototype: clean, well-tested, zero-dependency, and
already addresses most of the optimization items from the earlier report.

The prototype has evolved significantly beyond its original roadmap. The
devdoc/optimization-report.md is now OUTDATED — most P0/P1 items have been
implemented. The comparison below reflects the current codebase state.

4. DESIGN STRENGTHS OF GOPI
============================

4.1 Clean Separation of Concerns
    - deepseek/ package: pure API client, independent of agent logic
    - tools/ package: pure functions, no side effects, easily testable
    - agent/ package: orchestrates the loop, owns the context
    - cmd/agent/: minimal CLI glue
    This is better layered than pi-mono where agent-loop.ts mixes LLM
    calls, tool execution, and event emission in one file.

4.2 SSE Implementation is Excellent
    - Clean buffer sizing (64KB scan buffer, 2MB max line)
    - Proper [DONE] handling
    - Streaming tool call fragment merging by index
    - RawArgs accumulation for incremental JSON fragments
    - Fallback to non-streaming Chat() when stream fails
    This is production-quality code.

4.3 Retry Logic is Solid
    - Exponential backoff with configurable jitter
    - Respects Retry-After header on 429
    - Handles network errors (DNS, timeout, connection refused)
    - Debug logging for retry visibility
    - Non-retryable errors fail fast
    - Comparable in quality to pi-mono's provider-retry.ts

4.4 Context Window Management is Smart
    - Rough token estimator (chars/4 heuristic)
    - Trims oldest messages at 90% threshold
    - Never leaves orphaned tool messages
    - Configurable via GOPI_CONTEXT_WINDOW env var
    - pi-mono needs transformContext callback for this; GoPi does it automatically

4.5 Tool Error Messages are LLM-Friendly
    - "Missing required parameter: path" — model can self-correct
    - "is a directory. Did you mean ...?" — path suggestions
    - "Similar directories: ..." — directory name suggestions
    - Large file guidance: "Use offset/limit to read partial content"
    This is a clever design decision that helps the model recover.

5. CRITICAL DESIGN CONCERNS
============================

5.1 [HIGH] System Prompt is Never Set
    ----------------------------------
    Agent.SystemPrompt field exists but main.go never populates it.
    The model receives no system prompt, so it does not know it is a
    coding agent with tool access. This likely degrades initial tool-use
    quality.

    Fix:  In main.go, read GOPI_SYSTEM_PROMPT env var, fall back to a
          sensible default. Example:
            "You are GoPi, a coding agent. You have tools (read, write, 
             edit, bash) to help with software development. Think step 
             by step. Use tools when needed. Be concise."

5.2 [HIGH] Reasoning Effort Not Exposed
    ------------------------------------
    ChatRequest has ReasoningEffort and Thinking fields, but they are
    never populated. DeepSeek V4 supports reasoning_effort and thinking
    modes. Without these, the model runs in default mode which may be
    suboptimal.

    Fix:  Read GOPI_REASONING_EFFORT and GOPI_THINKING env vars.
          Wire them into the ChatRequest in loop.go.

5.3 [MEDIUM] No Safety Hooks for Destructive Operations
    ----------------------------------------------------
    pi-mono has beforeToolCall/afterToolCall hooks that can block
    dangerous operations. GoPi has RejectDangerous for bash but no
    general mechanism. The model could write to or edit critical files
    without confirmation.

    Current mitigation: bash danger patterns (rm -rf /, sudo, etc.)
    Missing: no confirmation for writing to existing files, no
    restriction on which directories are writable.

    Consider:  Add a --confirm flag that prompts on stderr before
               write/edit/bash execution. Or add before/after hook
               interfaces to Agent.

5.4 [MEDIUM] No Conversation Persistence
    -------------------------------------
    Session logs are write-only JSONL files. There is no way to resume
    an interrupted session. pi-mono supports tree-structured conversation
    persistence.

    Consider:  Add a --resume SESSION_ID flag that reads the session
               JSONL, reconstructs the message context, and continues.

5.5 [MEDIUM] Tool Execution is Sequential Only
    ------------------------------------------
    For each assistant message, tools execute one at a time in a for-loop.
    pi-mono supports parallel execution for independent tool calls (e.g.,
    reading two different files simultaneously).

    Impact:  Minimal for most use cases. Only matters when the model
             calls multiple independent tools in one response.

5.6 [LOW] Single Provider Lock-in
    ------------------------------
    The entire codebase assumes DeepSeek API format. While this is
    OpenAI-compatible, switching providers requires code changes.

    Consider:  If multi-provider support is desired, abstract the
               client interface (Chat, ChatStream) behind a Provider
               interface. This would enable Anthropic, OpenAI, etc.
               But this conflicts with the "zero deps, simple" philosophy.

5.7 [LOW] No Abort Signal During Tool Execution
    --------------------------------------------
    The agent has a 5-minute context timeout but individual tool
    execution (bash with timeout) cannot be cancelled by the user.
    pi-mono propagates an AbortSignal through the entire stack.

    Consider:  Use context.WithCancel and wire signal handling (SIGINT)
               to cancel the current operation.

6. ARCHITECTURAL CONCERNS FOR FUTURE GROWTH
============================================

6.1 The "Zero Dependencies" Tension
    --------------------------------
    GoPi's key advantage is the static binary with zero dependencies.
    Every feature added (OAuth, multi-provider, skills, extensions)
    increases code size and complexity. There is a natural tension
    between "simple prototype" and "full-featured agent."

    Recommendation:  Decide what GoPi IS. Is it:
      (a) A minimal, hackable reference implementation of the ReAct loop?
      (b) A production-ready alternative to pi-mono in Go?

    If (a): Keep it under 1000 lines, document it well, let users fork.
    If (b): Add provider abstraction, config system, safety hooks.

6.2 Settings/Config is Fragmented
    -------------------------------
    Configuration comes from multiple sources:
    - Environment variables (DEEPSEEK_API_KEY, GOPI_DEBUG, etc.)
    - ~/.gopi/settings.json (api_key, base_url, model)
    - Command-line flags (--settings)
    
    There is no unified config struct. Each package reads env vars
    independently. This works for a prototype but will become unwieldy.

    Consider:  A single Config struct populated at startup, passed to
               all subsystems. This also enables "gopi config show"
               for debugging.

6.3 Logging Has Three Separate Systems
    -----------------------------------
    1. Stderr output (real-time streaming + status line)
    2. FileLogger (~/.gopi/logs/gopi-*.log) — leveled, timestamped
    3. SessionLogger (~/.gopi/sessions/*.jsonl) — structured events

    All three are best-effort (errors are logged and ignored). This is
    fine for a prototype but makes debugging configuration issues hard.

    Consider:  At minimum, print a summary at exit: "Log: ~/.gopi/logs/..."
               "Session: ~/.gopi/sessions/....jsonl"

6.4 Token Estimation is Crude
    --------------------------
    chars/4 heuristic significantly underestimates CJK text and
    overestimates code with lots of whitespace. The API returns
    authoritative token counts in Usage, but these are only used
    for cost tracking — not for context window decisions.

    The current approach is "safe" (under-estimate → trim early),
    but may trim too aggressively for code-heavy conversations.

    Consider:  A running average correction factor based on
               API-reported tokens vs estimated tokens from
               previous requests.

7. WHAT GOPI DOES BETTER THAN PI-MONO
======================================

7.1 Deployment Simplicity
    - Single binary: `go build` → one file, scp to server, run
    - pi-mono: requires Node.js 20+, npm install, 100MB+ node_modules

7.2 Code Understandability
    - ~500 lines of Go with a clear control flow
    - pi-mono: agent-loop.ts alone is 792 lines in a sea of packages

7.3 Tool Error Messages
    - GoPi's tools return LLM-actionable error messages with suggestions
    - pi-mono relies on the model to interpret generic OS errors

7.4 Context Window Management
    - GoPi does it automatically before every API call
    - pi-mono requires explicit transformContext configuration

7.5 Static Analysis Friendly
    - Go's type system catches many errors at compile time
    - TypeScript catches some, but pi-mono uses many `any` types in
      tool execution paths

9. KEY INSIGHT
==============

The devdoc/optimization-report.md is now significantly outdated. GoPi has
already implemented all P0 and most P1 items from that report:

  P0.1 Retry with backoff           → DONE (retry.go, 130 lines)
  P0.2 Streaming agent loop         → DONE (loop.go chatOnce, with fallback)
  P1.1 Token/cost tracking          → DONE (CostTracker in types.go)
  P1.2 Context window awareness     → DONE (TrimToFit, ContextWindow)
  P1.3 System prompt injection      → PARTIAL (field exists, never set)
  P2.1 Reasoning effort config      → PARTIAL (types exist, not exposed)
  P2.2 Finish reason handling       → DONE (loop.go: length, content_filter)
  P2.3 Tool argument validation     → DONE (validateToolArgs in loop.go)

The two remaining lowest-effort, highest-impact changes are:
  (1) Set a default system prompt
  (2) Expose reasoning_effort/thinking configuration

Together these are ~25 lines of code and would bring GoPi to near-feature
parity with pi-mono's core agent loop while maintaining its key advantage:
a single, zero-dependency, instantly-deployable binary.
