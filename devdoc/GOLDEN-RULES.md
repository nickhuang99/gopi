# 金句汇档：架构哲学的凝结（可引用的判断，不是格言）

> **本档的规矩**：每条金句必须配两样东西 ——
> ① **它从哪个具体事故/数据里来**（不是空想）
> ② **它能指导什么具体行为**（不是感受）
>
> 一条金句如果给不出这两样，就不该进这个档（它只是好听）。

---

## 1. 教训与需求是同一件事的两面

> **教训是回望（我学到什么），需求是前瞻（接下来该做什么）——它们是同一件事的两面。**

**从哪来**：设计"主动产出需求"机制时发现，它需要的判据（可重复模式 / 可复现闭环 /
收益达标）与 lesson 三条件**完全一致**。两者都是"从经历中提炼可复用的东西"，
只是一个向后看、一个向前看。

**指导什么**：
- 不发明新标准——`brew` 的 lesson 判据直接复用到"改进提案"生成
- 反过来也成立：**如果一个"教训"无法转成"下一个该做什么"，它可能只是观察，不是教训**

---

## 2. 闭环需要三条腿（本档最重要的一条）

> **记得住（存储）→ 找得到（检索）→ 想得起来要用（自觉调用）。
> 前两条是机制，第三条是能动性。
> "主动"的本质，是在行动之前先问一句：我是不是曾经知道过这件事？**

**从哪来**：nick 对"存了不查等于白存"的补全。

三层失效模式，一层比一层深：

| 层 | 失效形态 | 性质 | 能否用机制修 |
|---|---------|------|------------|
| 存 | **存了不查 = 白存** | 存储失效 | ✅ 能（加索引、加触发） |
| 查 | **查了不用 = 白查** | 检索失效 | ✅ 能（改检索、加注入） |
| 用 | **想不起来要查 = 白有** | **意图失效** | ❌ **不能——这是能动性本身** |

**"主动"与"被动"的精确分界**：

- **被动** = 等上下文把它推到我面前（注入 / 提醒 / 报错撞上来）
- **主动** = **我先知道自己缺什么，然后去取**

**指导什么**（这是硬约束）：
- 任何"依赖 LLM 自觉查记忆"的设计**视为不可靠**
- "先查"必须像 Rule 5（build + test）一样成为**不可跳过的前置步骤**
- **不许写"agent 应该记得查"**——那和"agent 应该不硬编码"是同一类空话
  （本项目已验证：LLM 知道原则 ≠ 写代码时应用它）

**实证反例**：Bond 花 10 分钟探索公司自己的 memory sync 机制——
不是因为它不知道有 memory，而是**它没想到"这件事可能已经有人做过"**。
第三条腿缺失的直接代价。

---

## 3. 原则无效，检查才有效

> **LLM 知道原则 ≠ LLM 会应用它。陈述原则改变不了行为，可机械检查的规则才能。**

**从哪来**：反复验证——
- 工具名硬编码 23 处（问它"该不该用常量"它答得对）
- `taskSessionsRootName` 定义 1 次裸写 10 次
- `except:pass` 静默吞错（吞掉过 NameError、ESCAPE 语法错误、绑定计数不匹配）
- nick 原话："我本来以为 LLM 在预训练已经成熟了，没想到还是像初学者"

**指导什么**：
- 每条规则必须附**机械检查方法**（工具名/命令/测试），否则不是规则，是愿望
- 修 263 处 `%v`、52 处吞错这类问题，靠"教育"无效，靠 `errorlint`/`errcheck` 有效

---

## 4. 不引入比威胁更危险的防护

> **防护机制本身的危险必须严格小于它所防的危险。
> 否则净效果为负——"我们不能为了防危险而引入更危险的东西"。**

**从哪来**：PA 提出"全局扫描杀孤儿进程"的 watchdog，nick 质疑"它自己会不会是杀手"。
实测证实：本机合法的 `PPID=1` 常驻有 Xvfb / sshd / dbus / ollama /
**gopi task merger**——按"PPID=1 + 名字像测试"去杀，**立刻误伤**。

**关键不对称**（这是判据的核心）：

| | 事后清理 | 事前限制 |
|---|---|---|
| 失效后果 | **删错 / 杀错东西**（可能正在跑的关键任务） | **退化为无保护**（=事故前的状态，不更糟） |

**指导什么**：优先选"失效后退化"的方案，而不是"失效后误伤"的方案。
落地形态：cgroup 限制 + 创建者自清 + 命名空间隔离，而不是全局扫描杀进程。

---

## 5. 防患胜于未然：限制优于清理

> **与其事后检测并杀死，不如事前限制它能消耗什么。限制比清理安全，
> 因为限制不会误判"谁该被杀"。**

**从哪来**：nick 在 watchdog 讨论中定调（"防患胜于未然"）。PA 实测验证：
- `IOWriteBandwidthMax=/dev/sda3 8M` → 同一 dd：75MB/s → **7.9MB/s**
- `MemoryMax=64M` → 申请 300MB 被 OOM（exit 137），**机器毫发无损**
- `systemctl kill -s SIGKILL <scope>` → **一次干掉整组，不用猜任何 PID**

**指导什么**：压测/测试/agent 生成的命令跑在受限 scope 里（带宽+内存+时限三重保险）。

---

## 6. 全流程 = 存储链条完整（不是功能列表齐全）

> **对每一环问：这一环的产出，下游环节能不能在不重新劳动的前提下取到？
> 答"得重新查 / 重新读 / 靠人记得"——这条链就是断的。**

**从哪来**：nick 的"全流程掌控者"目标 + AI 智能体本体论
（**能力上限由存储结构决定，不由推理算力决定**；DFA→PDA→图灵机每次进化，
升级的都是存储结构与寻址机制）。

**指导什么**：
- 加新功能必须回答"它补的是哪一环"，**答不出来 = 可能是功能堆积**
- agent 退化成"每次重新开始的 DFA"不是模型弱，是**某两环之间的信息只在上下文里**

---

## 7. 反馈的确定性决定难度（软件 vs 机器人）

> **软件 agent 与机器人 agent 的差别不在"手脚"，而在反馈的确定性。
> `go test` 给你 exit code，传感器给你一张有噪的图。**

**从哪来**：nick 的"机器人原理一样，只是环境不抽象规整"。
PA 精确化：这也是 Computer Use 的难度排序——
**纯文字界面最容易（文字是 exact feedback），通用图形界面难（像素是 noisy feedback）**。

**指导什么**：判断一个自动化任务难不难，先看**它的反馈有多确定**，而不是看操作多复杂。

---

## 8. 模仿人类的鲁棒，而不是追求机器化的精确

> **人类做法往往比机器化的精确方案更鲁棒，因为天然带反馈。**

**从哪来**：nick 对 webcam POC 放弃原因的阐述——
"人类操作鼠标不是基于精确坐标，而是移动+看反馈+调整"。
开环绝对坐标结构性失败（光学误差 ~100px vs 点击目标 20×20px）。

**指导什么**：
- 需要"绝对精确"的方案先问：**能不能改成闭环？**
- 闭环让很多缺陷不再是缺陷（人类戴眼镜歪头照反光照样用电脑）

---

## 9. 工具数量本身就是成本

> **工具数量 = 注意力成本。每加一个工具，都在消耗每一轮的推理预算。**

**从哪来**：实测 gopi 10 工具 / dsh 25 / claude ~80 → 同任务 **5 / 6.5 / 17.4 分钟**。

**指导什么**（分层原则）：

| 需要的形态 | 放哪 | 注意力成本 |
|-----------|------|-----------|
| 需要 LLM 在主循环里决策调用 | 内核工具 | 昂贵（每轮全量发送）→ 必须少而精 |
| 不需要主循环决策，但要能跑 | CLI 子命令 | **零** |
| 偶尔用的重活 | 外部工具 | 零 |
| 只是配置/数据 | settings / DB | 零 |

---

## 10. 注意力不对称：测试代码的隐性代价

> **人对生产代码上心（出事直接暴露），对测试随意（不出事没人管）。
> 但在 agent 系统里，测试是唯一常驻运行的代码——**
> **生产代码只在被调用时跑，测试每天跑成千上万次。**

**从哪来**：nick 指出"测试代码粗心造成的破坏不可小视"。实测证实：
**测试代码 86,737 行 > 生产代码 72,473 行**，且从未被 code review。
2026-09-11 事故的凶手 `suite-ab.sh`（`while :; do dd ... conv=fsync; done`）
**就是测试代码**——它把整台机器打瘫。

**指导什么**：测试代码的审查标准**不低于生产代码**；测试的资源纪律是独立审查项。
