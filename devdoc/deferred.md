# deferred —— "想到但先不做"清单（append-only）

> **只追加，不删除。** 条目一旦写入就留在原处，像账本一样（append-only）：想法后来被做掉、
> 被否决、或变得无关，都只**追加**一条状态说明，**不改写也不删掉**旧行。
> 删除会让"上次那个想法呢？"变成无法回答的问题——那正是本文件存在的理由。

**注：本文件在 `devdoc/DOC-INDEX.tsv` 中的类目是 `historical`**（因此头部有 `<!-- doc-class: historical -->` 横幅），
这是分类器给出的判决 —— 分类器把"文档里出现任务号"读成了"这是一次运行的记录"。类目只决定**是否按锚点腐烂门禁**，
对本文件的功能无影响；但一个**前瞻清单**被判为"过去运行的记录"是分类器的已知偏差，记在此处免得未来读者困惑。
（类目由生成器写，不手改 TSV —— 规则 36。）

## 哪些东西不在这里

| 东西 | 它该待的地方 |
|---|---|
| 已立项、会有人去执行的工作 | 任务账本（`gopi task list`）——本文件**不是**任务队列 |
| "我们朝哪儿建"的阶段性架构计划 | `devdoc/roadmap.md` |
| 已修掉的缺陷、已落地的决定 | 对应 devdoc / `CONFIG.md` |
| 已否决并已有定论的方案 | `devdoc/` 里对应的决策文档 |

**本文件绝不产生 `pending` 行。** 它的存在，正是因为操作者否决了"用 `deferred` 标签 / 新任务状态"
来实现这件事（2026-09-29）：一个**永远不会被执行的 `pending` 行**只会让 `gopi task list` 更难读，
操作者原话——"否则我一直看到 pending 不能被执行更加的混乱"。标签只是过滤器的名字，问题没有被解决。

## 条目形状

每条**至少**这四段，缺一不可：

- **日期** —— 想法出现的日子（`YYYY-MM-DD`）
- **想法** —— 一句话说清要做什么
- **为什么先不做** —— 真实理由（依赖未就绪 / 成本不划算 / 现在做会固化缺陷 / 没有证据）
- **将来若做，第一步是什么** —— 一句**可执行**的起步动作（不是"研究一下"）
- **前提 / 依赖**（有则必写）—— 不写清依赖，未来会把它做成错的东西

## 2026-09-29 · 内存上界 + 从 raw log 回滚历史

**想法。** 给会话历史一个内存上界：把已渲染的历史从内存里放掉，需要时**从 raw log 读回并重放渲染**，
让内存占用与会话长度脱钩（长会话不再线性吃内存）。操作者 2026-09-29 原话："内存的事情不用急，
我只是希望你能把它记录下来。"

**为什么先不做。**

1. **它没有独立的正确性。** 回放出来的"历史真相"的正确性上限 = **转义解析器的正确性**。
   解析器仍有缺陷时，回放会把缺陷**固化成历史**——比现状更糟：现在的缺陷只是"屏幕上看错了"，
   回放会变成"记录里就是错的"。该缺陷此刻有**两条活任务**（见下）。
2. **写盘这一半已经没问题。** 写盘节流已存在：实测本会话 `dump 82KB` 覆盖
   `frames=24003 / snapshots=3849`。缺的不是"raw log 存不下"，而是"读回来能正确重放"。
3. **终端侧还有一条独立限制。** dump 自述 `interior_scroll_loss`：被**内部滚动区**挤掉的行是
   **终端丢弃**的，不是 gopi 保存的。所以"历史可回滚"还依赖"gopi 绝不去设会挤掉行的
   interior scroll region"——那是另一条约束，不是同一个修复。

**前提 / 依赖（必须先满足，顺序不可换）。**

- **必须排在 `01a0e81b-dc17-7756-b9e3-ad7d4701260f`（转义序列碎片/吞字 解析器修复）之后。**
  它是本条的**正确性前提**，不是"顺便一起做"的邻居。
- 同一条依赖链上的证据补充：`01a0e825-8fbf-7684-a48a-aa674c274252`——同一根因的另一半
  （序列在分帧边界被切开 → 真文字被吞、尾巴多出 `1m` / `;61H…`）。
- 策略前提：`01a0e834-1340-736d-a5f3-948dad0b68c3`——gopi 的 UI 取向是
  **append-only 直写 + 四层格式分层，不做可寻址重绘**。本条**不得**反过来引入重绘状态机：
  回滚要么是"重新 append 一段重放的输出"，要么不做。
- 可能的同源兄弟：`01a0e806-659a-7e91-a05d-462b43171453`（高亮区间整体前移 17 列）。
  若它与解析器缺陷同根因，本条应等它们一起收口，否则回放会把同一个错误重放两次。

**将来若做，第一步。** 先写**离线重放对账**：读一个**已存在**的 raw log → 重放 →
与同一会话**已有的 dump** 做 grid **逐列**比对，把"重放是否可信"变成一个数字。
**对账不过，本条直接关闭**（那时该修的是解析器，不是内存）。

## 2026-09-29 · `devdoc/roadmap.md` 已过时，该如何处置

`read/write/edit/bash`；而 gopi 现在是 17 个工具 + 任务账本 + 合并器 + 自感知 UI。

（`01a0e806` 列偏移 17 列、`01a0e81b-dc17` + `01a0e825` 转义泄漏与吞字）**全部是"回头改已画内容"的产物**。

在分层还没落地、缺陷还没收口之前谈检索，会把重绘从后门放回来。

**前提 / 依赖。** `01a0e834-1340-736d-a5f3-948dad0b68c3`（四层格式分层先落地）
