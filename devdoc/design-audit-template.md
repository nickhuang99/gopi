# 设计文档 ↔ 源代码一致性审计：模板

每个模块一份报告，落在 `devdoc/design-audit/<模块ID>-<slug>.md`。**六节，顺序固定，不得增删节。**
读法：先读本模块代码面与设计文档，再逐节填；**填不出来的节写"无设计文档"或"未观察到"，不写"大概/应该"。**

## 硬性要求（每条裁决必须满足，否则报告不合格）

1. **每条裁决指到两处**：代码侧 `路径:行号`（或 `路径:符号名`，符号须 `code_search` 命中）；
   文档侧 `路径:行号`。**只有一侧 = 证据不全**，须在裁决里显式写"文档侧无出处"。
2. **裁决三选一，逐条给**：`一致` / `不一致` / `无设计文档`。**"无设计文档"是裁决，不是遗漏** ——
   代码有该行为、文档没写，才算；代码没有该行为，那是不一致。
3. **不一致项必须编号**：`U-<模块ID>-<两位序号>`（如 `U-M02-01`），并写：现象、代码出处、文档出处、影响、建议动作。
   **编号是下游收口的接口**（A-X01 汇总这些编号）。
4. **长度上限：一屏两屏**（约 60–120 行）。超了 = 该模块没切够 —— 退回 `design-audit-modules.md` §4，
   把它按职责子链拆成两个子任务，**不要写一份更长的报告**。
5. **不改生产代码、不移动任何文件**：本审计只产出报告与编号；归档/改文档是下游任务的动作。
6. **结论要可被推翻**：每条`一致`都必须给出"我是怎么确认的"（命令或 `code_search` 结果），
   避免"看着像"。**没有确认动作的`一致`，等价于没审。**
7. 结束时跑 `gopi doccheck`（exit 0）——报告本身也是一篇 devdoc，必须被分类。

## 第 1 节 设计怎么说

设计文档**意图与约束**的摘要，**每条带文档行号**。写法：

```
- 设计主张：<一句话>　出处：devdoc/requirements/03-worktree-and-cwd.md:41
- 设计主张：<一句话>　出处：GOPI.md ## Rule 30（Rule 30，无行号则记条目号）
```

**本模块无设计文档时**，本节不空着：写"无设计文档"，并列出**散落的准设计文本**及其出处
（`GOPI.md` 规则条、`CONFIG.md` 行、专题 devdoc 的行），说明为什么它们不足以充当设计。
散落文本的清单本身就是"该新建"裁决（第 6 节）的输入。

## 第 2 节 代码怎么做

只列**观察到的事实**，每条带 `file:line`（函数名 + 关键行）。写法：

```
- `internal/tools/task_finish_cleanup.go:1455` `finishCleanupServerRecycle` —— 释放场地前调用交付点同步
  （`internal/tools/task_finish_deliverysync.go:364` `finishCleanupLocalSync`）
- 观察到：settings.json `sync_peers: []` 时 `HasSyncPeers()` 为假 → 客户端臂整段不可达
```

**顺序按执行路径**（谁调用谁），不要按文件字典序 —— 审计对象是流程，不是目录。

## 第 3 节 逐条裁决

本节是报告的主体，一行一条，**三列语义（设计/代码/裁决）**：

| # | 设计主张（§1 的出处） | 代码事实（§2 的出处） | 裁决 |
|---|---|---|---|
| 1 | 交付前必须与集成分支对齐（`3c396080` 提交信息） | `internal/tools/task_finish_deliverysync.go:…` | 一致 |
| 2 | 预合并构建失败必须拒绝交付 | `task_finish_deliverysync.go:…` | 一致 |
| 3 | （无设计主张） | `internal/runend/runend.go:…` | 无设计文档 |

**一致性判定的口径**：设计说的**约束**（必须/禁止）在代码里能被指出**强制点**才算`一致`；
只说"做了这件事"而没有强制点的，判`不一致`并编号。

## 第 4 节 边界

- **本模块负责**：<列 2–4 条，与 `design-audit-modules.md` §2.1 的名字一致>
- **本模块明确不负责**：<写清"读起来像本模块，其实归谁"> —— 越界是划分缺陷的证据，须记入第 6 节
- **越界发现**：若本模块代码实现了邻居的职责（或反之），记 `U-<模块ID>-xx`，并指出该文件应该归哪个模块。

## 第 5 节 未实现或有边界实现

设计写了、代码**没做**或**只做了一半**的清单。每条写：

```
- U-Mxx-nn：设计要求 <…>（文档:行）；代码只在 <条件/file:line> 下实现，其余路径静默通过。
  建议动作：<补实现 / 改文档 / 降级为已知边界并写进文档>
```

**边界实现也算发现**：`sync_peers` 为空时某一臂不可达，就是这一类（真缺陷不必是崩溃）。

## 第 6 节 文档该改 / 该归档 / 该新建

三条出口，各自带**动作 + 目标路径 + 依据**：

- **该改**：`devdoc/<x>.md:行` 的哪句断言已不成立，改成什么（一句话写清新表述）。
- **该归档**：`devdoc/<x>.md` → `devdoc/archive/`，依据 = `design-audit-modules.md` §3.1 的 L1–L4 哪条不满足；
  **执行步骤见该文件 §3.2（四件套 + gate 影响），本报告只提出、不执行。**
- **该新建**：本模块缺哪份设计文档、放哪、需要包含哪几节（用本模板的第 1/4 节当骨架）。

## 报告尾部（固定）

```
## 审计范围与实际观察
- 范围：代码面 <读过的文件数 / loc>、文档面 <读过的文档与行数>（对照模块清单的声明值，差异写出来）
- 未覆盖：<本 session 没来得及看的子链 —— 明确写出来，别假装全覆盖>
- 复核命令：<跑过的 code_search / doccheck 命令与结果>
```
