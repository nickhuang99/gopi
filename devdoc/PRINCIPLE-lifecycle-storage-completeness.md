# Rule 16: Lifecycle Storage Completeness — every stage's output must be addressable downstream

## 这条规则解决什么

gopi 的目标是**掌控软件工程全流程**（需求→调研→记忆→教训→工具安装→环境→代码浏览
→撰写→测试→调试→bug汇报→任务调度）。功能会越来越多。

**但"功能多"不等于"全流程掌控"**。真正的判据是**存储链条的完整性**：

> 对每一环问：**这一环的产出，下游环节能不能在不重新劳动的前提下取到？**
> 如果答案是"得重新查 / 重新读 / 靠人记得"，那这条链就是断的。

依据（AI 智能体本体论）：**能力上限由存储结构决定，不由推理算力决定**。
DFA→PDA→图灵机的每次进化，升级的都是**存储结构与寻址机制**。

**推论**：agent 退化成"每次重新开始的 DFA"，不是因为模型弱，而是因为
**某两环之间的信息只存在于会话上下文里**（会话结束即消失）。

## 规则

### 16a. 每一环的产出必须落在可寻址的存储上

**不是"记在上下文里"，而是"能被下一个任务检索到"。**

判断一个产物是否"落盘"：

| 落盘 ✅ | 未落盘 ❌ |
|---------|----------|
| `memory.db`（可 FTS5 检索） | session JSONL（会被 trim，且跨会话不可直接检索） |
| git 分支/commit（权威） | 只在当前上下文里的推理 |
| `tasks` 表（有状态机、可查询） | 打印到 stdout 就丢了 |
| `sessions/<id>/attachments/`（有 manifest） | 存在 `/tmp`（会被清、在 boot device） |
| devdoc（有索引） | 靠人记得 |

### 16b. 加新功能时，必须回答"它补的是哪一环"

新功能的价值判据**不是"它有用"**，而是：

- 它把哪一环的产出**从"仅会话"提升到"可寻址"**？
- 或者它让哪一环的产出**能被下游消费**？

**如果答不出来，它可能只是功能堆积，不是链条补全。**

### 16c. 断链点必须被显式列出，而不是隐含

维护一份**断链清单**（本规则附带的表），每次发现新的断链就登记。
断链的定义：**信息只存在于会话上下文里**。

**当前已知断链（2026-09-11 盘点，详见
`devdoc/agent-full-lifecycle-chain-audit-20260911.md`）**：

| # | 断链点 | 后果 | 状态 |
|---|--------|------|------|
| 1 | **调研结论不沉淀**——查完就丢，下个任务重新查 | 重复调研，浪费 token | 待验证（01a08d94） |
| 2 | **代码理解不沉淀**——同一模块反复探索 | 重复劳动 | 待验证（01a08d94） |
| 3 | **调试根因不沉淀**——同类 bug 重复踩 | 高频损耗 | 待验证（01a08d94） |
| 4 | **环境状态无权威视图**——"装没装/什么版本"靠猜 | 反复确认 | 待验证（01a08d94） |
| 5 | **需求动机不留痕**——执行者不知"为什么" | 易走偏 | 待验证（01a08d94） |
| 6 | **测试基础设施不可靠**——scratch 隔离残缺 | 🔴 2026-09-11 事故源 | 修复中（01a08d7e / 01a08d67-cc86） |
| 7 | **记忆自动查用无保证**——存了不查 = 白存 | 存储浪费 | 部分缓解（pre-llm 注入） |

### 16d. 主动产出需求的地基：先修链条，再谈主动

"从被动接受指令 → 主动发现并提出问题"是 nick 定的方向（**能动性/意识的起源**）。

**但顺序不能倒**：

```
主动产出需求  依赖→  记忆链路是通的
                     否则产出的提案基于残缺认知
                     （不知道历史、不知道现状、不知道已试过什么）
```

**先把"记住"做扎实，再谈"主动"。**

已有的地基（可复用）：
- `task_submit` 通道（**已验证**：LLM 自投 bug 单质量高——五要素齐全）
- reframe 三档（把模糊意图转成可执行判据：DOABLE/TOO_BIG/IMPOSSIBLE）
- brew + lesson 三条件（可重复模式 / 可复现闭环 / 收益达标）
- priority 派生（tags→priority）

**关键洞察**：**"值得沉淀的教训"和"值得提出的需求"是同一件事的两面**——
教训是回望（我学到什么），需求是前瞻（接下来该做什么）。
所以主动产出需求的第一个可落地形态：

> **执行 → 提炼 pattern → 达到阈值（重复 N 次 / 影响面大）→ 自动 submit 改进提案**

判据复用 lesson 三条件，不发明新标准。

### 16d-2. 闭环需要三条腿（nick 补全，2026-09-11）

上面那句"两面"是对称的一半，**完整闭环还需要第三条腿**：

```
记得住（存储）   →   找得到（检索）   →   想得起来要用（自觉调用）
   机制问题            机制问题             ★ 意图问题 = 能动性的本质
```

- **存了不查 = 白存**（存储失效）
- **查了不用 = 白查**（检索失效）
- **知道要去查 = 主动性本身** ← 这一层不是机制能解决的

**"主动"与"被动"的精确分界**：

| | 定义 |
|---|---|
| **被动** | 等上下文把它推到我面前（pre-llm 注入 / 有人提醒 / 报错撞上来） |
| **主动** | **我先知道自己缺什么，然后去取** |

**"想得起来要用"的本质 = 在行动之前先问一句："我是不是曾经知道过这件事？"**

这一问本身就是能动性。它不需要新工具，需要的是**把"先查"变成默认动作**——
而这又回到本项目的铁律：**原则无效，检查才有效**。
所以"先查"不能靠自觉，必须像 Rule 5（build + test）一样成为**不可跳过的前置步骤**。

**落地要求**：任何"依赖 LLM 自觉查记忆"的设计都视为**不可靠**。
要么做成 harness 前置步骤（开工前强制检索，成本固定），
要么做成钩子（在关键决策点注入检索结果）。**不许写"agent 应该记得查"**。

### 16e. 优先复用，不新建 store / 守护进程 / 工具

补链条时**优先复用** `memory.db` + 现有工具面。

理由：**工具数量本身是注意力成本**（实测：gopi 10 工具 vs dsh 25 vs claude ~80
→ 同任务 5 / 6.5 / 17.4 分钟）。每加一个工具都在消耗每一轮的推理预算。

分层原则（按注意力成本）：

| 需要的形态 | 放哪 | 成本 |
|-----------|------|------|
| 需要 LLM 在主循环里决策调用 | 内核工具 | 昂贵（每轮全量发送）→ 必须少而精 |
| 不需要主循环决策，但要能跑 | CLI 子命令（`gopi X`） | **零注意力成本** |
| 偶尔用的重活 | 外部工具（vcmi / wine / playwright） | 零（CLI 调用） |
| 只是配置 / 数据 | settings.json / DB | 零 |

## 为什么这条规则要用"检查"而不是"原则"

本项目已反复验证：**陈述原则改变不了行为，检查才能**。

所以本规则的**可执行部分**是：

1. **新功能检查**（提交 PR / task 时）：它补的是哪一环？产出落在哪？
   → 答不出来 = 可能是功能堆积
2. **断链清单**：每次发现新的"信息只在上下文里"就登记（它是活文档）
3. **修复优先级**：断链的修复优先于新功能（反馈可靠性 > 功能数量）
