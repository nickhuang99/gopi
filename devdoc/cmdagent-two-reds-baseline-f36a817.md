# Two `cmd/agent` reds at the baseline — one already fixed upstream, one a real mis-report

Two tests in `cmd/agent` were red at the baseline `f36a817`, reproduced there by a
sibling run in a detached control worktree. They turned out to have **nothing in
common**: one was a stale generated document whose fix already existed on master but
was not in the baseline the bug was filed against; the other was a real defect with a
one-word root cause, and it was the defect that mattered.

## Defect 1 — `TestManSourcesMatchTheirHelpPage/gopi-version.md`

**Root cause: a generated man document was never regenerated.** `b18e2e180`
(`fix(briefing): re-measure a briefing's quoted population FIGURE at dispatch, and
report artifact deploy drift`) added a `--drift` paragraph to `gopi version -h`
(`cmd/agent/cli_version.go`). The man corpus is GENERATED by
`internal/standards/testdata/mancensus.go` from the built binary's help pages, so the
hand-written half of `man/gopi-version.md` was correct while the `<!-- BEGIN SYNOPSIS -->`
region still held the pre-`--drift` text. `6d17ef5c7` regenerated it — five lines, the
only file in that commit.

**The baseline-membership fact is what the bug report missed**, and it is decided from
the object store, not from a diff:

```
$ git merge-base --is-ancestor 6d17ef5c7 f36a817 ; echo $?   # 1  → the fix is NOT in the baseline
$ git merge-base --is-ancestor b18e2e180  f36a817 ; echo $?   # 0  → the offending commit IS
```

So the red was real **at `f36a817`** and is already repaired on master; at this run's
cut (`e12c50f`) the subject passes without any change from this branch.

**Red proof, reproduced without checking out the old baseline** — the baseline content
of the one generated file, restored over the fixed tree, turns the subject red again:

```
$ git show f36a817:man/gopi-version.md > man/gopi-version.md
$ go test ./cmd/agent/ -count=1 -run TestManSourcesMatchTheirHelpPage   # exit 1
--- FAIL: TestManSourcesMatchTheirHelpPage (2.35s)
    --- FAIL: TestManSourcesMatchTheirHelpPage/gopi-version.md (0.01s)
$ git restore --source=HEAD -- man/gopi-version.md
$ test "$(git hash-object man/gopi-version.md)" = "$(git rev-parse HEAD:man/gopi-version.md)" && echo RESTORE-OK
```

"Not regenerated by hand" held: the acceptance run below is the project's own check
(`go run internal/standards/testdata/mancensus.go . bin/gopi --check`), and it reports the
whole corpus up to date.

## Defect 2 — `TestMergeUnrelatedHistoryBranchIsDiagnosedNotAnError` (the real one)

**Symptom.** The report did not name the archive tag, while the run had in fact written
it:

```
    merge_unrelated_history_test.go:156: the report does not name "archive/feat/orphan-…"
      …feat/orphan-… unrelated-history  shares no commit with master …; roots …;
      left as it is, NOT retired: archive retirement reconcile: no ledger at
      /dev/shm/suite-cmd-agent-run-…/003/memory.db
```

**Root cause — one word: an absence reported as a refusal.** The retirement's ledger half
opens the process's ledger through `archiveRetirementLedger`, whose own doc comment
already stated the rule:

> An ABSENT ledger is the empty answer, never a refusal — the same read guard
> `taskOwnerAxesAll` obeys (`ledger_read_guard.go`)

The code contradicted its comment:

```go
if ledgerMissingForRead(path) {
    return nil, fmt.Errorf("archive retirement reconcile: no ledger at %s", path)
}
```

That error travels up `ReconcileUnrelatedHistoryRetirement` →
`mergeUnrelatedHistoryOutcome`, which renders **any** error as
`mergeUnrelatedHistoryLeftAsIsFmt = "left as it is, NOT retired: %s"` — the sentence
reserved for "the writer did not run", printed over a writer that had just written both
the archive tag and the reason record. The test is not over-strict: it asserts the
report and the write agree, and the run printed the opposite of what it had done.

**Why it is the ordinary case, not an edge.** A host that has never filed a task has no
ledger, so every fresh machine and every fixture takes this arm — which is exactly why
the bug was reachable in a package fixture pinned by `t.Setenv("GOPI_MEMORY_DB", …)`,
and why it survived: with the shared `/dev/shm` suite home this is the *steady state*,
not a race.

**Two sites, because the absence is one fact and reached the caller twice.**
`archiveRetirementLedger` now answers the empty case with a **nil handle** (its comment's
rule, in code), and `archiveFamilyRowsForBranch` — the only reader of that handle —
treats `nil` as **zero rows**. Without the second edit the nil handle would have
panicked; with it, the reconciliation reports "nothing to reconcile" without inventing an
error to say so. Every **writer** in the file keeps its own opener
(`retiredBranchReconcileDB`), whose unavailable-ledger path still logs rather than
silently dropping the trail write.

**No guard was weakened.** The error arm is still reachable and still asserted: a ledger
that EXISTS and cannot be opened as one is genuinely "I could not look" (Rule 15) and
must not be flattened into the reassuring empty answer —
`TestArchiveRetirementReconcilesWhenTheLedgerIsUnreadable` seeds a directory at the
ledger's path and requires the error to survive; `ledgerMissingForRead`'s own semantics
are untouched.

## The guards

| Guard | Pins |
|---|---|
| `TestArchiveRetirementOnAHostWithNoLedgerIsNotARefusal` | absent ledger ⇒ no error; the tag and the reason record are still written; the decision is read back; the ledger is NOT created by the read path |
| `TestArchiveRetirementReconcilesWhenTheLedgerIsUnreadable` | its mirror: a present-but-unreadable ledger still reports the failure |

Both assert the **outcome the writer produced**, not merely "err == nil" — a reconciler
that returned no error and reconciled nothing would fail them.

**Red proof (measured):** restoring the old `fmt.Errorf` line alone turns the first guard
red with its own diagnosis, and it was restored by content identity:

```
--- FAIL: TestArchiveRetirementOnAHostWithNoLedgerIsNotARefusal
    archive_row_reconcile_test.go:327: an absent ledger was reported as a failure:
    archive retirement reconcile: no ledger at /dev/shm/suite-tools-run-…/memory.db —
    `gopi merge` renders this as `left as it is, NOT retired`, i.e. a refusal to the
    operator over a write that succeeded
$ sha256sum -c archive_row_reconcile.fixed.sha256   → …: OK
```

## The real surface (Rule 31)

The whole defect was reproduced and repaired through the CLI, on a repo built in
`/dev/shm` (device 28, off `/` — device 2051) with **no ledger**:

```
$ GOPI_HOME=… GOPI_SETTINGS=… ./bin/gopi merge            # fixed binary
  …refs/heads/feat/orphan-real unrelated-history  …; retired as a decided exclusion
   (tag archive/feat/orphan-real, reason unrelated-history) — the branch ref is preserved; …
$ git for-each-ref → refs/gopi/archive-reason/feat/orphan-real, refs/heads/feat/orphan-real,
                     refs/heads/master, refs/tags/archive/feat/orphan-real
```

and the same scenario with the **pre-fix** binary (built with `go build -overlay`, so this
worktree was never mutated) prints the lie the fix removes:

```
$ … gopi-prefix merge
  gopi merge: feat/orphan-real: unrelated-history retirement not written:
      archive retirement reconcile: no ledger at …/memory.db
  …; left as it is, NOT retired: archive retirement reconcile: no ledger at …/memory.db
$ git for-each-ref → (identical four refs — the write HAD happened)
```

Two observations make the defect's cost concrete: the refs are identical in both runs
(the tag was written either way), and the second run's warning plus its "NOT retired"
verdict are both false statements about its own completed write.
