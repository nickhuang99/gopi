## Findings

**Zero P0, zero P1.** All findings are P2 (robustness/hygiene) or N (design note). The critical claims
hold — foreign DBs are never mutated and a broken DB cannot cause conclusion fabrication (write-side
surfaces errors; the read side is guarded by the dirty-latch order).

The table is created ONLY by `ensureSessionConclusionsSchema` (writetaskarea.go:61), called lazily from WriteTaskArea's own open (105). **Real consequence of the drift — pre-feature DB read path**: SessionConclusions on an old DB (table absent) runs tableExists (173) → `ok=false` → `return nil,nil` (174-175) — safe, no write-path precondition needed. Both guarantees the claim names (pre-feature DB gains it; foreign DB never mutated) **hold in practice** — but via openTasksDB's ownership gate + lazy create, not via the named heal functions. | 2 | P2 | memory.go:381-402 (openDB), 876 (ensureKnowledgeBase), 884/905 (openTasksDB); writetaskarea.go:105,170 | **Read path opens RW, never readOnly.** WriteTaskArea (104) and SessionConclusions (169) both call `openTasksDB(ctx, memoryDBPath())` → `ensureKnowledgeBase(ctx,path,false)` / `openDB(path,false)` — never the readOnly=true variant (which only openSearchDB uses). So SessionConclusions — a "read-only carry-forward" — still opens the DB **read-write**, running the full gopi-ownership probe + ensureTasksSchema DDL storm on every call, and would happily write if a bug ever introduced a write. ensureKnowledgeBase's readOnly param (876) is unused by the task-area path. Consequences: (a) a genuinely read-only DB file (chmod a-w, e.g. a mounted snapshot) makes SessionConclusions' openTasksDB fail → swallowed to nil,nil (Finding 6); (b) per-call DDL storm cost (R1 #8) is doubled — every commit round pays 2 opens (1 write + 1 read-inject) each running the ownership probe + ensureTasksSchema. A readOnly open + tableExists would serve the read path with zero mutation risk. |
| 3 | P2 | writetaskarea.go:44-49 (schema), no DELETE/UPDATE/VACUUM anywhere | **Unbounded append-only growth with no cleanup — but bounded in practice; no archive parity needed (see text).** keyword_search confirms zero DELETE/UPDATE/VACUUM/auto_vacuum on session_conclusions anywhere in the repo. Each run appends rows scoped by session_id forever. Quantified: real ~/.gopi/memory.db has **34 rows / 13 sessions over ~6h** of active multi-agent use. A ~200-char row is a few hundred bytes in the file; a session commits ≤ ~10 conclusions (each requires a distinct subtask item). Even at an extreme 100 rows/run × 100 runs/day × 365d ≈ 3.6M rows ≈ **~1 GB/year** — but reads are `WHERE session_id=?` over the indexed column, so per-session cost is constant; only the file bloat grows. The read is additionally gated by tableExists on EVERY open. **Ledger parity analysis**: the tasks table has `TaskArchive` (tasks.go:2794) but that is a *soft tombstone* (tags += "resolved") — it never DELETEs rows; even the append-only task_events audit table has no prune. So session_conclusions lacking cleanup is **consistent with every other table in the DB** — no inconsistency, no P2 escalation. Watch item (not a defect): the single row-deletion path in the whole DB layer is the repo-guard test helper; production relies on VACUUM-by-backup for physical shrink (per nightshift-report pattern). If a future feature ever DELETE+reuses session ids, the AUTOINCREMENT guard (Finding 4) is what keeps ordering sound. |
| 4 | N | writetaskarea.go:43 (AUTOINCREMENT), 177 (ORDER BY created_at, id) | **Ordering/append-only correctness — sound.** `id INTEGER PRIMARY KEY AUTOINCREMENT` (43): AUTOINCREMENT (not plain INTEGER PRIMARY KEY) guarantees ids are never reused after a delete (sqlite_sequence), so cross-restart monotonicity holds even if a cleanup is ever added. `ORDER BY created_at, id` (177): created_at is REAL UnixNano/1e9; two commits within float64 mantissa resolution (~2.4e-7 s at epoch scale) are impossible on the tool's real path (WriteTaskArea is one tool call per LLM round), and even then the `id` tiebreak resolves it. Sequential commits in the same second pass the ordering test implicitly (writetaskarea_test.go:39-57). Schema heal idempotence: CREATE TABLE IF NOT EXISTS + CREATE INDEX IF NOT EXISTS on every open is the ensureSchema pattern (safe, ~0.2ms in WAL per the enableWAL comment). **Concurrency**: two gopi runs on the same DB — CREATE IF NOT EXISTS is a write txn; _txlock=immediate + busy_timeout=15000ms (openDB, memory.go:381-390) makes the loser queue on the write lock instead of failing SQLITE_BUSY; the same busy handling the ledger uses everywhere. Benign. |
| 5 | P2 | writetaskarea.go:160-166 (SessionConclusions err→nil,nil) vs 105-107 (WriteTaskArea err→surfaced) | **Error-swallowing asymmetry assessed — NOT a P1, and the H4 fabrication risk is closed by the dirty-latch ordering (closes R1 #3's R3 cross-check).** SessionConclusions returns nil,nil on (a) empty sessionID (158), (b) openTasksDB error (160-166), (c) tableExists error/absent (173-175). A permanently broken/locked/corrupt DB would make every SessionConclusions silent-empty → injectTaskAreaConclusions no-op. **Why this cannot cause H4 (fabrication)**: the runEngine hook (loop.go:2927-2931) runs `injectTaskAreaConclusions()` then `trimCommittedTaskArea()` ONLY when `a.taskAreaDirty` is latched, and the latch (4221-4222) is set ONLY after `tools.WriteTaskArea` returns nil — i.e. after a *successful* DB insert on the same DB. A DB so broken that the read fails empty would have failed the write that sets dirty; no commit → no inject → no trim → committed region stays intact. The swallow is therefore safe on the realistic corrupt-DB path and justified by the doc'd "read-only carry-forward must never fail a run". Contrast is real but benign: WriteTaskArea surfaces open errors loudly (the write must not pretend success); SessionConclusions' contract is "absent = empty" and every swallow site is a genuinely absent-DB/table case on the write-guarded path. Minor note: a transient DB failure between a successful write and the inject read (e.g. another process holding an exclusive lock for >5s) would drop that round's carry-forward while dirty stays latched and trim still runs — a 1-round conclusion absence. Window is tiny (two opens are ~ms apart) and the trim only removes *committed* regions whose conclusion is re-injectable next successful read. Not a P1; log the swallowed open error at debug level if observability is wanted. |

Not a bug; a design note that the table mirrors the ledger's shape but silently chose a different timestamp resolution. `1e9` is an unnamed unit-conversion literal (Rule-1 scope = timeouts/limits — N). |
