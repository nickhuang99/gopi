## Findings (found while writing the tests — reported, not patched)

1. **`gopi archive <branch> --repo PATH` ignores `--repo` for the ARCHIVE
   action.** The page documents `--repo PATH   Repo to inspect/act on. Default:
   the repo of the cwd`, and `gopi archive --check --repo PATH` resolves it —
   but the archive action resolves the repository from the CWD regardless:

   ```
   $ cd /tmp && gopi archive fix/broken --reason compile-failure --repo /path/to/fixture
   gopi archive: git rev-parse --show-toplevel in .: exit status 128:
     fatal: not a git repository (or any of the parent directories): .git           (exit=1)
   $ gopi archive --check --repo /path/to/fixture
   archive backlog: /path/to/fixture   clean — every archive tag over a …          (exit=0)
   $ gopi archive --check --repo /nope
   gopi archive --check: git rev-parse --show-toplevel in /nope: chdir /nope: …    (exit=1)
   $ cd /path/to/fixture && gopi archive fix/broken --reason compile-failure --repo /path/to/fixture
   archived fix/broken as archive/fix/broken
     reason: unowned
   ```

   The `--check` rows above are the evidence that the flag is READ on that path
   (its message names the path it was given, `/nope`, and resolves a real one).
   The archive ACTION prints `in .` and resolves the CWD, so the same documented
   flag is honoured by one subcommand and ignored by the other.

   The exit code is 1 (measured: `env -i … gopi archive fix/broken --reason
   compile-failure --repo /path/to/fixture` from `/tmp` → `exit=1`), so the
   failure is reported, not swallowed — the defect is the IGNORED `--repo`, not
   a silent success. The cases therefore chdir into the fixture repo — the
   page's own examples carry no `--repo`, so that is the shape its examples
   assume.
2. **RETRACTED — no defect here.** An earlier draft of this report claimed
   `gopi --bogus-flag` did not fail on an unknown top-level flag when followed by
   an unreadable `@file`. Re-measured with the exit code captured directly (not
   through a pipe), the flag is refused in every ordering:

   ```
   --bogus-flag @/nope/missing.txt   exit=1 | gopi: unknown flag --bogus-flag
   --bogus-flag --prompt hi          exit=1 | gopi: unknown flag --bogus-flag
   @nope/missing.txt                 exit=1 | Error reading @ payload file … no such file
   ```

   The original reading came from a pipeline whose `$?` was the consumer's, not
   the command's — the same mistake as the first finding's exit code. Recorded
   because the CORRECTION is the finding: a `.sh`-piped exit code is not the
   command's exit code, and both claims here were made from one.
