    fix(daemon): fold every /proc/net/unix row for a path — one connect() puts a client row first
    
    The unlinked-yet-bound positive control (TestUserBusProbe_RealUnlinkedSocketIsDetected)
    failed on this host: observeUserBusPath reported listen=false, inode=0 for a socket
    that was bound and listening at an unlinked path.
    
    Neither candidate cause held. A raw /proc/net/unix dump around the unlink
    (session dir, tmpfs and block device) shows the row SURVIVES the unlink with its
    inode unchanged, and the field indices (St=5, Inode=6, Path=7) are right for the
    row shape this kernel emits — field[0] is the row's address LABEL, so the columns
    sit one position right of proc(5)'s header, and the path landing at [7] is how you
    tell. The defect was the LOOKUP, not the table:
    
      the kernel copies the bound path into EVERY AF_UNIX socket's address
      (unix_mkname), so ONE client connect() renders a SECOND row for the same path —
      St=02, Inode=0, the client's socket object — and emits it FIRST. A scan that
      returned at the first matching row described the CLIENT. observeUserBusPath
      dials, so the client row existed before the unlink.
    
    userBusKernelBinding now scans the whole table and folds it (userBusFoldUnixRows,
    pure): bound is set by the LISTENing row wherever it sits, that row's inode is
    reported, and the row count is kept as evidence. Two adjacent repairs: an
    unreadable table is an error classified unknown instead of reading as 'nothing is
    bound' (Rule 15), and the fixture's socket path is checked against sun_path (108)
    with bind's EINVAL distinguished from the filesystem's — on a suite root under
    /run/user the nested names reached exactly 108 bytes and bind answered EINVAL.
    
    Tests: the live control now connects a client and holds it across the unlink,
    proving >1 row carries the path; the fold's order-independence is a pure test over
    verbatim rows (the kernel picks the order, so the dangerous one is exercised as
    values); an unreadable table classifies unknown, not fault.
    
    Verified on both roots (tmpfs suite root and /run/user/1000): PASS. The same
    invocation on the unmodified baseline FAILS, so the pass is attributable.
