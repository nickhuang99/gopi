# Task Report: ab3 harvest/claim same-id collision audit (hp) — 2026-09-04

Audit of the cross-node sync channels (harvest + claim-lock) for the
same-second id-collision silent-loss class the `task-id-collision` epic
protects against — but only on SOME code paths.

## Scope

Reviewed the three cross-node row-sync surfaces in `internal/tools/`:

- **import channel** — `importTaskExisting` (task mirror import): REFUSES /
  relabels same-id DIFFERENT-work collisions.
- **harvest channel** — `harvestReconcile` (peer reconciliation): gates the
  equal-stamp branch AND the pending-collision relabel on `harvestSameContent`,
  but **NOT** the strictly-newer branch.
- **claim channel** — `syncClaimRemoteRow` (M4.21 claim-lock verbs): only
  status-CAS verbs; **zero content gates anywhere**.

Verdict: the anti-silent-loss protection (relabel/refuse on content
mismatch) is applied inconsistently across the three channels. Two of the
three have it; the third has none, and the harvest channel skips it on one
branch.

## Findings

### DEFECT 1 — harvest strictly-newer terminal-over-LIVE overwrite (no sameContent gate)

`harvestReconcile`'s "remote strictly newer" branch (memory_sync_task.go
~1777-1797) unconditionally calls `harvestUpdate` when a strictly-newer
remote **terminal** row meets a locally-**LIVE** (claimed/in_progress) row
of DIFFERENT content. The equal-stamp branch (~1755-1769) and the
pending-collision relabel (~1693-1737) both gate on `harvestSameContent`;
this branch does NOT. `harvestUpdate` (~1837+) overwrites
payload/summary/status unconditionally.

Failure: a same-second id collision where the peer's row (different work)
went live+terminal on the peer strictly later than this node's live row →
this node's live run's content is silently replaced by the peer's different
work and marked completed. The exact silent-loss bug the id-collision epic
exists to prevent — protected in the pending/equal-stamp cases, missing on
this path.

### DEFECT 2 — PushTerminalTaskSync rides the claim-remote handler that refuses terminal verbs

`PushTerminalTaskSync` (M4.19 ②, commit `021754e` 07:27) sends a
just-terminal row verbatim via `exportClaimPatch` over the claim channel;
its peer handler `SyncClaimRemote` then called `SyncTaskImportDelta` (the
applyNewer ladder — terminal rows accepted). Commit `db22503` (09:17, same
day) REWROTE `SyncClaimRemote` into the M4.21 lock-verb switch
(`syncClaimRemoteRow`: only in_progress acquire / pending revert; default
REFUSES "unsupported claim verb status"). `021754e` is an ancestor of
`db22503`.

Result: a terminal row (completed/failed) pushed to a peer that HOLDS the
row (the normal two-node mirror topology, the M4.21 双锁齐 shape) is
REFUSED every retry → `PushTerminalTaskSync` errors → terminal-push-failed
alarm — but the row never lands on the peer's mirror, and the stale comment
at `db22503:625` still claims the applyNewer ladder accepts it. The M4.19 ②
must-succeed guarantee is orphaned: only a ghost peer (never saw the row)
accepts.

### DEFECT 3 — claim-channel acquire verb hijacks a divergent pending row

`syncClaimRemoteAcquire` (M4.21) is a pure status CAS —
pending→claimed→in_progress — with ZERO content gate (`memory_sync_claim.go`
has no `taskIDRelabel` / `WorkHash` / `SameContent` anywhere). The import
channel (`importTaskExisting`) and harvest channel (`harvestReconcile`) both
relabel/refuse same-id DIFFERENT-work collisions; the claim channel does
not.

Failure: same-second id collision leaves a divergent pending row on the
peer (the peer's own different work under the SAME `t-<sec>` id) → a remote
runner's Phase-2 acquire hijacks it: the peer's pending row flips to
in_progress (`claimed_by` stays empty) and the peer's dispatcher can no
longer claim it (a claimed/in_progress row is not claimable). The peer's
genuinely different task silently loses its queue slot.

### DEFECT 4 — harvest strictly-newer terminal-over-PENDING fabricates a completion

Same root cause as DEFECT 1, distinct victim state: local **pending** row
(work A, queued never-run) + strictly-newer remote terminal row with
DIFFERENT content B → `Migrated=1`, row fabricated-completed with B's
content. The v1 import channel explicitly REFUSES this shape
(`importTaskExisting` "refusing to fabricate a completion") and the harvest
relabel comment claims the same, but relabel only fires for
remote-live/pending, never the strict-newer terminal path.

## Root cause family

The same-second id-collision protection (task-id-collision epic) is
inconsistently applied across the three sync channels:

- **import channel**: protected (refuse/relabel on content mismatch) — v1.
- **harvest channel**: protected on equal-stamp + pending-collision paths,
  MISSING on the strictly-newer terminal-over-live/pending path (DEFECTS 1+4).
- **claim channel (M4.21)**: protected NOWHERE — acquire is a blind status
  CAS (DEFECT 3); terminal pushes are refused by the verb switch (DEFECT 2).

The M4.21 rewrite replaced the generic delta merge (import-style
protection) with verb-scoped CAS handlers and never carried the content
gate across.
