# Chat 自观测的 dump 归属：身份走进程树，拒绝代替猜测

**一句话**：一个 chat run 在**自己的环境**里发布「我是哪个 surface」
（`GOPI_CHAT_SURFACE_ID=<pid|self>:<session-dir>`），它的 bash 子进程继承这份身份，
于是 `gopi ui_state --target chat` 认领的是**本 run 自己的** dump；声明对不上且候选
不止一个时**拒绝**（并列出声明、pid 与 `--pid` 出路），绝不退回「最像的那个」。

## 为什么需要这条通道（问题的形状）

`gopi ui_state --target chat` 的通用规则是 `uiclient.SelectLive`：**唯一 live 的
surface 就是它，多一个就拒绝**。这在只跑一个 chat 时没问题，但操作者的 chat 与 agent
自己的 chat 同时在一个 profile 上跑是**常态**——此时通用规则唯一能做的就是把两个
candidate 列出来然后拒绝，而调用方（它是其中一个 surface 的**子进程**）手里明明握着一个
扫描永远推不出的事实：**我属于哪一个**。所以拒绝在这里是正确的，但无用。

## 为什么是环境变量，而不是文件/锁/daemon/新子命令（Rule 35）

这个事实的**生命周期恰好等于一个进程**，需要的读者**恰好是它的后代**——这正是
`exec(2)` 已经免费携带的东西：环境随 fork+exec 复制，进程退出由内核回收，没有任何东西
需要被创建、查找、归属、老化或垃圾回收。写一个 pid 文件或 dump 旁边的标记，就是为
「随进程而死的事实」买一个**持久依赖**：多一个 artifact，多一个没人拥有的生命周期。
所以通道取进程树自带的那一条，最小权限的拼法是一个变量。

## 为什么值是「声明」而不是「授权」

值被读到时**不做任何授权**：它只与**已经自证过身份**的产物比对（dump 自己的
`(pid, started)` 戳对 `/proc`，`uiclient.dumpIdentityVerdict`）。因此伪造值、陈旧值、
畸形值都只会**退化为通用规则**，并把这次 miss **说出口**（Rule 15），而不会变成「静默
地读别人的屏幕」——后者正是这条能力存在要消灭的缺陷。

## 三条裁决，各有理由

| 情形 | 答案 | 理由 |
|---|---|---|
| 声明命中恰好 1 个 | 它（并报出命中哪一半：`pid` / `session` / `pid+session`） | 唯一确定 |
| 声明命中 ≥2 个 | `AmbiguityError` | 声明覆盖了两个 artifact，就是两块它无法选择的屏幕 |
| 声明 0 命中、候选 ≥2 | `SelfIdentityMissError`（拒绝） | **绝不退化成「最像的那个」**：那会把别人的屏幕交到以为在看自己的调用方手里 |
| 声明 0 命中、候选 =1 | 它（说成「只有这一个」） | 没有可与它混淆的对象；这也是 `SelectBySession` 的同一支，保证「身份没能发布」的 run 行为不变 |
| 没有声明 | 规则**自报未适用** | 「没发布」与「发布了对不上」是两件事；前者必须回到通用规则 |

「未适用」用一个单独的 `available bool` 返回而不是一个 error：一个只返回 error 的规则
会让调用方把「没有声明可用」当成「被拒绝」而停止读一块它本来读得到的屏幕。

## 写点为什么只有一处

`installChatSurface` 是 run 的 **arm 点**，也是身份两半（本进程 pid、本 run 写 dump 的
session 目录）同时存在的唯一缝隙。在同一处发布，声明与屏幕就不可能互相说谎：一个缝，
每个 chat run 走一次。

## 诚实的两处「不做」

1. **不静默替换**：任何 arm 都只在自证过的候选里选，对不上就说。
2. **不静默降级**：`os.Setenv` 失败时打印未发布句子（说清变量名、想发布的值与原因），
   因为「子进程将退回通用规则、而通用规则在多 surface 时拒绝」是操作者必须能看到的因果。

## 复现/取证方式（Rule 31，可复用）

`testsuite/chat_surface_identity_e2e_test.go` 是这条通道的**端到端取证**：真 `gopi chat
--tools --dump-screen` + 真 pty + MockLLM，让模型调 `bash` 跑
`"<bin/gopi>" ui_state --target chat`（**不带** `--pid`/`--session`），然后断言
tool_result 里的 `dump=` 是本 run 自己的 session 目录、`pid=` 是 **chat 进程自己的 pid**
（测试从未把这个 pid 写进任何环境——它只能来自 chat 进程自己的 `os.Setenv`）。这条断言
就是「继承真的发生了」的证明，而不是「动词会读一个环境变量」的证明。

一个可复用的实测坑：工具结果有**截断预算且保留尾部**（本次实测 header 被切掉、24 行 grid
完整保留），所以断言「顶部的观察行」时要在命令里用 `sed -n '1,Np'` 只留下头部——这不改变
动词的运行参数与账本，只决定断言看得到哪些字节。
