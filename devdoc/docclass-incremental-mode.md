# docclass incremental add mode — landing one doc without regenerating the corpus

`devdoc/DOC-INDEX.tsv` is GENERATED by `tools/docclass/classify.py` and gated by
`internal/standards`. Before this mode existed a file that landed under `devdoc/`
had exactly two ways to gain its row, and both were wrong for a single new doc:

- **hand-edit the manifest** — a row typed by hand drifts from the generator
  (a different reason sentence, a stale evidence anchor), and the drift is the
  recurring docclass-red family;
- **regenerate the whole corpus** — correct bytes, but the regenerate is not a
  no-op on a drifted manifest: measured on base `98e8941c` (clean tree, no new
  doc at all) it rewrites **128 rows across 128 files: 14 class flips and 114
  evidence/reason drifts**, every one of them a row some other in-flight change
  owns.

## The mode

```
python3 tools/docclass/classify.py . --add-missing        # add a row for every devdoc file that has none
python3 tools/docclass/classify.py . --only PATH          # (re)write the row for one path, in place
python3 tools/docclass/classify.py . --add-missing --dry-run   # print the row(s), write nothing
python3 tools/docclass/banner.py . --only PATH            # the banner companion, same two shapes
```

Both writers go through ONE row renderer (`row_text`) and ONE classifier
(`classify_one`), so the row an incremental run writes is byte-identical to the
row a whole-corpus run writes for the same file: measured, `cmp` of the two
generated rows is empty.

The incremental writer does NOT re-sort the file. It carries every existing row
over byte-for-byte at its existing position and splices only a path that was not
there before, at the whole-corpus sort position — so the diff is a PURE
INSERTION (`git diff --numstat` = `1 0`), which is what a merge needs. Sorting
the file was measured to be wrong: the checked-in manifest is not in generator
order (rows have been appended by hand), and re-sorting it rewrote three
unrelated rows.

Idempotence holds: a second `--add-missing` run adds nothing (`added: 0`), and a
second `banner.py --only` reports `applied to 0 docs`.

## Order and population

Per-file classification is **order-independent** and **population-dependent only
in the evidence cell**, measured on the full corpus (2270 docs) by replaying
every document's verdict under three arms:

- reversed traversal: **0 differing docs** — order does not enter the verdict;
- a minimal population (the repo-wide index narrowed to the files that doc
  itself references): **67 differing docs — 1 class change, 66 evidence/reason
  changes**.

Both arms of the incremental mode build the FULL repo-wide Go/citation index and
never read a manifest row, so neither shape is reachable from the mode: the row
it writes is the whole-corpus row. The minimal-population arm is the shape a
future "classify one file in isolation" implementation would get wrong, and it
is why classification takes the whole-repo index rather than the manifest.

## Why there is no Go-side enforcement

The landing path already resolves a conflicted manifest mechanically
(`cmd/agent/merge_union.go`, `mergeUnionArtefacts`): rows from both sides are
unioned and `mergeUnionNoRowLost` refuses a union that drops a row or duplicates
one — a classification is never lost. The pre-land gate
(`cmd/agent/merge_preland_gate.go`) additionally refuses a hand-resolution that
silently changes a document's class.

What no gate can do is WRITE the row. The merge lane resolves a manifest BOTH
sides already carry; `TestDocManifestCoversEveryDevdocFile` then fails until the
covered row exists, so a branch that lands a doc must land the row itself. That
is the gap this mode fills: it is the cheap, minimal, generator-exact way for
that branch to produce the row (and the banner) it owes.
