# 全流程链条盘点：从「需求提出」到「教训沉淀」的存储完备性审计

## 这份文档回答什么

the operator 的目标：**一个掌控软件工程全流程的 agent**（需求→调研→记忆→教训→工具安装→
环境→代码浏览→撰写→测试→调试→bug 汇报→任务调度）。

**判据（本盘点的核心方法）**：

> 把全流程拆成环节，检查**每一环的产出是否能被后续环节寻址到**。
> 如果某两环之间的信息**只存在于会话上下文里**（会话结束即消失），
> 那就是**链条断了** —— 不管功能列表看起来多齐全。

这与"AI 智能体本体论"一致：**能力上限由存储结构决定，不由推理算力决定**。
DFA→PDA→图灵机的每次进化，升级的都是存储结构与寻址机制。

**产出**：每个环节的 ①已有机制（带证据）②信息落在哪（DB / 文件 / 仅会话）
③缺口 ④**断链点**（信息只存在于会话中）⑤下一步该做什么。

---

## 采集方法（可复现）

```bash
# 工具面
gopi --help                     # 顶层动词
gopi task --help / memory --help / web --help

# 存储面
ls ~/.gopi/*.db                 # 有哪些 store
sqlite3 ~/.gopi/memory.db ".tables"
sqlite3 ~/.gopi/memory.db "SELECT COUNT(*) FROM <each table>"

# 会话面（是否只存在于上下文）
gopi log <session>              # 实际发送的内容
gopi stats <session>            # 轮次/token

# 代码面
ls internal/                    # 有哪些子系统
```

### 1. 需求提出（模糊意图 → 结构化判据）

## 二、断链点汇总（按严重度）

| # | 断链点 | 后果 | 修复方向 |
|---|--------|------|---------|
| 1 | **调研结论不沉淀**（第 2 环） | 重复调研，浪费 token（实证：探索自己的代码 10 分钟） | 调研产出强制落 memory（结构化：问题/来源/结论/何时有效） |
| 2 | **环境状态无权威视图**（第 5 环） | 装了/没装/版本全靠猜 | 环境探针 → memory 或独立 store（`gopi env` 视图） |
| 3 | **代码理解不沉淀**（第 7 环） | 同一模块反复探索 | 模块级索引（"X 做什么/在哪/依赖谁"）→ memory |
| 4 | **调试根因不沉淀**（第 9 环） | 同类 bug 重复踩 | 根因 → memory（带错误签名做检索键） |
| 5 | **测试基础设施不可靠**（第 6 环） | 🔴 **今天的事故源**；假红/假绿 | 已派 01a08d7e / 01a08d67-cc86 |
| 6 | **需求动机不留痕**（第 1 环） | 执行者不知道"为什么"，易走偏 | submit 时强制 why（或从对话提取） |
| 7 | **记忆自动查用无保证**（第 12 环） | 存了不查 = 白存 | pre-llm 注入（已有）+ 任务开始时的强制检索 |

## 三、核心结论：链条的"完整性"判据

**全流程 = 存储链条完整**，而不是"功能列表齐全"。

一个可检验的判据：

> **对每一环问：这一环的产出，下游环节能不能在不重新劳动的前提下取到？**
> 如果答案是"得重新查/重新读/靠人记得"，那这条链就是断的。

按这个判据，目前**最健康的链是**：

    bug 汇报 → 任务调度 → 代码撰写 → git  →（回到调度）
    （这条链的每环都有权威存储，且下游能寻址上游）

**最断裂的链是**：

    调研 → ?（丢弃）
    代码浏览 → ?（丢弃）
    调试过程 → ?（丢弃）
    → 教训总结 ← 只有"最终结论"能到这里，"过程"全丢

## 四、"需求提出/调研"环节的特别说明（the operator 点出的缺环）

**现状**：agent 是**被动接受指令**的——需求来自 the operator（或 PA 派工），agent 不产出需求。

**为什么这是关键缺环**：

自动化的等级可以这样排：

    1. 被动执行（给指令才动）           ← 我们现在在这里
    2. 被动执行 + 主动汇报（发现问题）
    3. 主动发现 + 自主提出（产出一等需求） ← 目标
    4. 自主选择方向（定义"该做什么"）

**我们已经在第 2 级的边缘**：LLM 自投 bug 单（`tags=bug`）已验证——agent 在
执行中发现缺陷并**主动提交工单**，而且质量高于多数人类 ticket（五要素齐全：
复现命令/现象/证据/背景/验收标准）。

**从 2 → 3 缺的机制**：

| 缺什么 | 具体形态 |
|--------|---------|
| **观察→模式的提炼** | 从"这次发现了 X"到"这类问题反复出现，值得系统性解决" |
| **主动调研的触发** | 什么情况下 agent 该去查资料而不是硬写？（现在靠 LLM 自觉） |
| **需求的自我产出** | agent 自己 submit 一个新任务（不只是 bug，而是**改进提案**） |
| **价值判断** | 产出 10 个提案，哪个值得做？（现在没有排序依据） |

**已有的地基**（可复用）：
- `task_submit` 通道（已验证质量）
- reframe 三档（把模糊转成可执行判据）
- brew（从执行记录提炼 pattern）
- priority 派生（tags→priority）

**所以"主动意识"的第一个可落地形态可能是**：
**执行 → 自动提炼 pattern → 若达到阈值（重复 N 次/影响面大）→ 自动 submit 改进提案**。

这和 brew 的 lesson 三条件（可重复模式 / 可复现闭环 / 收益达标）**判据完全一致** ——
即"值得沉淀的教训"和"值得提出的需求"是同一件事的两面：
**教训是回望（我学到什么），需求是前瞻（该做什么）**。

## 五、下一步建议（按 ROI 排序）

| 优先 | 动作 | 理由 |
|------|------|------|
| P0 | 修测试基础设施（已派） | 今天的事故源，且是"反馈可靠性"的地基 |
| P0 | **调研结论落 memory** | 断链最严重 + 立即可做 + 收益直接（省重复探索） |
| P1 | **调试根因落 memory**（错误签名为键） | 同类 bug 复发是本项目的高频损耗 |
| P1 | 环境状态视图（`gopi env`） | 消除"装没装/什么版本"的反复确认 |
| P2 | **主动需求产出的第一个形态**（pattern 阈值触发 submit） | the operator 的"意识起源"目标，需在断链修好后才可靠 |
| P2 | 代码理解索引（模块级） | 收益大但工程量大 |

**顺序理由**：主动产出需求（P2）**依赖**前面的记忆链路是通的——
否则 agent 产出的提案会基于残缺的认知（不知道历史、不知道现状、不知道已试过什么）。
**先把"记住"做扎实，再谈"主动"。**
