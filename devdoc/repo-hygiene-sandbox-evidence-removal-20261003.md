| `sandbox/**/.gopi/sessions/*.jsonl`, `raw/*.log` | **REMOVE** | recorded run transcripts; they are the operator's sessions, mirrored into a run scene |

| `.png/.jpg/.gif` under the devdoc evidence dirs | **REMOVE** | screenshots/frames = **regenerable artefacts**; the *recipe* that renders them is what belongs in the repo |
| `.wav/.pcm` and raw audio captures | **REMOVE** | capture output, reproducible from the capture script |
| recorded run logs (`*.log`, `*.err`, `*.txt` dumps, `.json` response dumps, `.html` bodies) | **REMOVE** | a transcript of one run; the run is not re-runnable from the repo, and the log is not text of record |

## Not Done (honest)

- **The operator's real data is ALREADY in git history and this commit does not
  remove it.** Removing the paths from the index stops them being *tracked going
  forward*; the blobs remain in every commit that carried them, reachable at the
  old revisions and clonable by anyone. Measured:
  `git rev-list --all -- sandbox/sbx/.gopi/memory.db` still lists the commits
  that carried it; the same is true for `sandbox/**/.gopi/sessions/*.jsonl`. See
  the risk section below — stated to be plain, not buried.
- **No history rewrite.** `git filter-repo` is absent on this host and
  `filter-branch` would write the **shared main `.git`** used by 5 worktrees and
  39 branches — out of scope **by design**, and Rule 35 forbids inventing a tool
  or dependency to do it. The removal therefore has a *forward* effect only.
- **The 72 kept paths under those dirs were not re-examined file by file.** The
  decision above is by class (extension + is-a-test-reader / is-a-product-reader).
  A `.py`/`.sh` that is itself a one-off dump would have been kept; none was
  found in the survey, and the survey is what the table above records.
- **The Rule 39 gate is PARTIAL** (its own doc says so): it keys on the index by
  content, so a blob reached through a variable, or untracked residue, is not
  caught. Untracked residue is Rule 30's business, and this run left none.
- **The text of this document changed in the `docs` commit, not the `chore`
  commit** — so the "830 rows pruned, 181 permits ratcheted" facts and their
  generating commands sit one commit away from the change they describe. That is
  the price of the rebase: the first attempt's prose carried the pre-rebase
  figures (813 rows, −200) and those figures are **wrong for this base**.
- **The two gate allow-lists needed a companion edit that this branch found by
  running them, not by reading the tree** (`e3a2279f`): the untracking deleted the
  paths that `rule35StateExemptRels` (the three committed `sandbox/**` trees) and
  `workerOwnershipDismissed` (a 720-line transcript under `devdoc/assets/`) existed
  to permit. Measured: at master `7e319ebd` the Rule 35 table held **5 permits**,
  all for paths this change removes — a permit whose file is gone is exactly the
  stale-permit ERROR Rule 39 names for its own baseline, and `rule35StateExemptRels`
  had **no staleness check at all**, so the entries would have outlived their files
  silently. The fix retires both (the Rule 35 table is now empty) and adds the
  missing staleness assertion to that gate, so the next such removal is caught by
  the gate rather than by a reviewer's memory.
- **8 pre-existing test failures in `internal/testutil` are NOT this change's.**

## Risk: the operator's real profile data is in the git history — and REMAINS there

**What was in the tree.** Three sandbox profiles in `sandbox/` carried
`memory.db`, `tasks.db`, `sessions/*.jsonl` and `raw/*.log` that were copies of
the operator's live `~/.gopi` data — 3 ledgers, 5 session transcripts, 5 raw
logs, all committed and pushed to the shared repo.

**What this run did.** Untracked them and deleted them from the working tree,
and made `/sandbox/` ignored so a copy cannot be re-added. It did **not** and
**cannot** un-commit them.

**Why the omission is deliberate, not laziness.** The only mechanisms that
remove a blob from history are `git filter-repo` (not installed) and
`git filter-branch` (writes the shared main `.git`, whose 5 worktrees and 39
branches would need coordinated rewriting and force-push) — plus every clone
that already holds the pack would have to be re-cloned. The session budget and
Rule 6 confine this run to its own worktree, and Rule 35 forbids installing a new
tool to do it. So the honest statement is: **the exposure is real, still live,
and out of this scope.**

**Recommendation.** Treat the leaked material as **disclosed**, not as
remediable by a later cleanup commit:

1. **Rotate what is actually secret.** If any key/token ever entered those
   `sessions/*.jsonl` / `raw/*.log` / `memory.db` rows, rotate it — a rewrite
   does not unring that bell, but rotation does.
2. If a rewrite is genuinely wanted, do it as its **own planned task**, on the
   main repo, with the operator present, all worktrees quiesced, a fresh mirror
   as the safety copy, and a coordinated re-clone of every peer — never inline in
   a hygiene commit.
3. Whatever the decision, **stop the source**: the cause was a sandbox profile
   authored inside the repo tree. `.gitignore` now covers `/sandbox/`; the
   durable fix is that sandboxes live where `gopi sandbox show` says
   (`config.ResolveSandboxRoot`), never under a checkout.
